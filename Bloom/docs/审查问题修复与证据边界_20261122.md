## 2. 必须先纠正的事实与口径

### 2.1 原flow任务按协议定义标签，但模型没有直接读取protocol字段

实际检查了CAIDA-flow、MAWI2020/2021/2022-flow及MAWI2024-flow的`data.npz`和`model200.txt`：输入均为`['src','dst']`、X两列、`max_feature_idx=1`，模型特征名为`src dst`。

构造源码：[prepare_datasets.py](../windows_research/round2_backlog/src/prepare_datasets.py)，第20行筛选src/dst，第24–33行说明flow key保留协议身份、X只取Source/Destination。原holdout预声明也明确是address-only。

因此要区分：

- **已确认的问题：任务的member/negative由UDP/TCP协议类别界定，支持集特殊，可能存在任务层面的协议分离捷径，不能代表一般KV membership。**
- **不准确的指控：模型直接把protocol或Label列当输入。** 本次检查不支持这一说法。

这个更正不消除代表性问题，也不把地址相关性当成普适可学习性。TCP-only及HTTP对照仍必要。

### 2.2 ClarkNet并非三个预算的FP中位数都胜Replay

32KiB下RA为137，Replay为134，所以RA稍差；RA-global为146，RA仍优于它。逐预算×seed的RA/Replay是8胜1负，与这个中位数结果不矛盾。

16KiB的RA/BF两个方法各自FP中位数是1221/1231；逐案例先算`(FP_RA+1)/(FP_BF+1)`再取中位数是0.968304。两种量不可相互替代。

### 2.3 0.941968不等于未经平滑的总FP降低5.8%

第37轮`miss/traffic`是9个配对的**加1平滑比值中位数**。可写“中位配对平滑比0.942”，不要改写为整个工作负载的总FP精确下降5.8%。9对共享同一日志；其中一对仅1138 vs1139，不能称作大幅或显著改善。

### 2.4 统计簇与胜出分母

1146原案例 → 排除70个probe案例后1076 → 按原reference FP>=30计入748。718/748的旧胜出结论必须携带这个限定；完整未筛选计数在档案中。

21个dataset×workload-group簇不是21个已证明独立的真实工作负载。第29轮按完整dataset重采样、保持原效应权重，index修复后的效果0.975084，95%区间[0.947281,1.001171]，原p=0.095799不变。只有8个命名dataset簇，这仍是有限集合敏感性分析，不是等效、非劣或总体普遍优越证明，也不因fp64的另一条区间较有利而移植到index。

## 5. 完整部署账本与保证契约

### 5.1 预算与placement

| 项目 | Filter Budget | 其他必须报告的成本 |
| --- | --- | --- |
| 最终模型数组、路由/阈值、BF、header、CLOCK缓存 | 是 | 完整实占，不只payload |
| 完整成员hash验证索引 | 否，属于声明的backend侧 | 缺少时8*n+header、构建、按需验证；已有时可复用，但资源本身并未消失 |
| 后端原始记录、精确keys、数据库索引/内部cache | 否 | 不可默认免费或为0 |
| 训练/评分、keys/counts/rates、候选和JIT/验证工作区 | 非最终Filter Budget | CPU、内存、准备成本单列；不把harness RSS说成Filter大小 |
| 特征提取、hash、query inference、prefix生成、network/SQL | 运行成本 | 只做flags回放时这些未全部测量 |

MAWI21 24KiB实例：Filter实占24163B，required index323400B，已知两项合计347563B。COD300万成员的索引payload是24000000B（24MB，约22.9MiB），不是全部backend/进程内存。

第39轮提供168行资源明细，但**没有因此声称完成相同全系统RAM上限、不同前后端placement的公平优化实验**。若8*n索引可在前端低延迟访问，它本身也可用于成员hash排查，应考虑直接索引对照；不能一面把它当无代价背景、一面不允许其他方法利用它。第35轮把它放在独立backend进程，验证的是那个明确部署设定。

原始key有序不意味着hash有序；不能假定B-tree/LSM天然提供安全prefix所需的排序hash索引。

### 5.2 正确性模式不能混用

| 模式 | 可以给出的保证 | 关键限制 |
| --- | --- | --- |
| Verified-prefix | 完整、同版本静态成员hash索引排除所有member后，cache不拒绝成员；完全hash别名或prefix过长bypass | 后端反馈与索引/成员状态一致；不能给动态更新无条件保证 |
| 精确uint64 key＋双射编码＋完整64-bit cache | 可以作为精确key缓存，不需要概率碰撞论证 | 必须是真正的精确key域，不是任意字符串已被压缩成64-bit ID |
| 更大原始key域的64-bit fingerprint | 可能因表示碰撞产生FN，有限样本0FN不等于不可能 | **共享hash入cache偏差使S/2^64容量界不能仅凭理想非恶意hash直接使用，见第40轮** |
| 精确原始key cache | 可提供精确匹配语义 | 可变长key、对象/header及存储均需计入预算；本轮未实现 |

第40轮用固定、非自适应的5个negative keys及精确概率分布给出容量界反例；不是找到了真实64-bit碰撞，也没有改变已有FP/FN记录。要保留容量型概率界，需独立证明指纹与cache入选过程的条件独立性；仅对同一个压缩64-bit值加盐不够。对预先固定的有限原始key集合可考虑Q/2^64、nQ/2^64的保守跨集合界，仍不是无限期或敌对键保证。

成员/hash版本变化需要失效或重新验证旧prefix；模型、预处理或路由变化需要相应BF重建并一致发布。模型改变不必在数学上使同成员/hash下的prefix证明失效，但当前实验没有实现或验证在线原子切换、cache迁移或并发更新协议，不能声称可以无协调替换模型。

### 5.3 学习开销：必须与同一个baseline做差

第39轮MAWI21 index案例，学习L=857343，尾段H=2572031：

| 比较对象 | 额外学习调用 | 尾段调用节省 | 学习＋当前尾段净节省 |
| --- | ---: | ---: | ---: |
| 已部署Plain BF | 587171 | 608853 | 21682 |
| 已部署BF＋固定10% warm Cache | 847009 | 27244 | -819765 |
| 共同采集标签后冷部署的学习选份额BF+Cache | 0 | 27313 | 27313 |

不是“学习85.7万次就多付85.7万次”，也不能将Gama的尾段节省与另一个baseline的学习成本拼接。相同成员访问在无FN时抵消。

42个index/fp64设置中，与已部署固定10% warm-cache BF相比，两格式各21例在当前学习＋尾段窗口内都净增加backend调用。若同享标签来源，尾段减少调用的则为index11/21、fp6410/21。**采集设定改变结论；这不是端到端时间测量。**

回本的显式模型为`ΔT(N)=A+ΔL*C/1e6+N*[d-(1-p)*s*C]/1e6`。A包含额外非lookup启动、学习处理、训练、索引、重配置净成本；C为基本backend调用成本，d为额外非lookup处理（含模型与prefix验证差额），p为成员比例。只有`(1-p)*s*C>d`才有持续收益斜率。周期性重建要重复计费，不能无限摊销一次startup。

若已有严格zero-FN且同快照的filter，拒绝本身可成为negative证书，只对放行查询查backend，可能避免增加标签采集调用。但需要完整入口日志/计数，而非只有backend日志；fp64 cache命中不可单独当严格negative证书。这是尚未实现的新采集协议，不能倒填到旧实验。

### 5.4 学习状态也不是总比原始流省内存

GT19源码的`state_bytes`仅计keys＋counts=16D；另有rates=8D，三数组payload24D。相对8L轨迹，阈值分别是D/L>1/2、D/L>1/3。第39轮15个不同dataset/seed输入中，分别2个、3个超过原始轨迹payload；例如MAWI20 TCP-only为1.433×和2.149×。这还不是含Population工作区或RSS的完整峰值估计。

## 6. 理论最优性、迭代与no-repeat的准确范围

### 固定T子问题

对固定模型/分区、固定非负M(T)、连续BF位预算，KKT给出

`epsilon_i = min(1, mu*n_i / ((ln 2)^2*M_i(T)))`，并需单独处理EMPTY/零质量等退化情形。

这不自动覆盖：离散树/份额搜索、动态T、4-way CLOCK、整数BF、floor/snap、GT估计误差、bucket精排或数据漂移下的完整选择器。

### Proposition5.3的精确条件

在正member支持上，p_j=n_j/n，r_j=M_j/h_j，且两种连续解都未截断时：

`F_h/F_M = (sum p_j*r_j) / exp(sum p_j*ln(r_j)) >= 1`。

这是加权AM/GM比，不是任意“方差越大收益越大”的定理；把全部r乘同一常数会改变普通方差，却不改变这个比值。截断时不能直接把该式当精确值或安全界。

第28轮117/168连续双内点的等式通过，但实体TTL/CLOCK有负结果、URL预测/实际关联较弱。第37轮也有3个miss对h退化。不要写成“所有实验完全吻合并验证全局最优”。

### 实现没有迭代到已证明收敛

冻结[ra4.py](../windows_research/round4_ra_plbf/src/ra4.py)第119–138行建立160点log T网格（另加T=0）；第231–253行`solve`做容量可行性搜索和默认**3次**set-associative refinement。它不是带收敛证明或残差停止证书的全局优化器。有限轮次给出有界工作量，不等于迭代已收敛。

本次没有新增收敛或最坏近似比证明。若不需要该更强性质，正确处理是明确完整selector为heuristic；若仍主张它，就必须另行给出数学条件与证明，而非用几条成功曲线代替。

### No-repeat和zero-tree是不同保证

- 原140例bit-identical是有限回归证据；评分/EMPTY处理与树排序条件不能省略。第30轮发现评分差异，但18个预定设置未找到选择逆序反例，不能把疑点写成已经构造出反例。
- [RA6-NR32](../windows_research/round32_no_repeat_guard/README.md)在非空、每key一次时直接调用项目内同一个`E5.gama`构建/选择路径；140回归和4重复控制通过。这是事后新变体，不是原RA6全称保证，也不是与作者官方Gama所有训练/部署状态逐位相同的主张。
- [ZGate](../windows_research/round20_zero_guard/README.md)是另一个事后变体：192例，112次选zero-tree，32 TCP-only全选BF，80强模型控制保留RA。对BF尾段无退化是该矩阵观察；对RA仍26例尾段退化。
- ZGate只保证学习段取两类finalist的较小FP，要付13个BF候选及回放成本；部署选zero-tree并不意味着搜索期没训练模型，也不继承49.24×选择加速或原no-repeat/Gama性质。取消的第21轮不重启。

## 8. 可供后续改稿使用的准确叙述（仅MD草案）

> 我们以缓存无法吸收的预期负查询质量重加权备份过滤器。在固定characteristic time的连续子问题中可得到解析最优分配；完整的离散、组相联候选选择使用启发式近似。在自然HTTP重复流上，固定模型、分区和缓存的消融显示了条件性的重加权收益，但整体learned方案并不稳定优于同预算BF+Cache。较长学习流的选择阶段可以显著减少候选回放成本；小学习流、廉价backend以及需要新采集标签或建立额外索引的部署可能不划算。

> Verified-prefix的零FN保证以完整、同版本成员hash索引及正确验证/失效协议为前提。一般key域的fingerprint cache采用不同正确性契约，不能等同于严格零FN；其概率界还需明确哈希与条目入选的依赖关系。Filter Budget不包含全部backend、学习和重配置资源，必须分别报告。

上面没有写入摘要、结论或任何论文文件，也不是接受决定的预测。
