# 基于 LightTree-PLBF 的轻量级 Learned Bloom Filter 优化

## 摘要

本项目围绕 Learned Bloom Filter 在有限内存预算下的误报率优化问题展开。最初我们复现老师提供的 Gama-LBF URL 实验链路，并实现了若干学生模型，包括单阈值 PiecewiseLinearLBF、LogisticFeaturePiecewiseLinearLBF、Raw-PLBF-Student 等。

实验逐步表明：单一 scorer + 单一 threshold 的 Learned Bloom Filter 表达能力有限，即使经过 segments、threshold、regularization、model type 等搜索，也难以稳定接近 G-LBF。随后我们将重点从“如何得到一个更强的全局 score”转向“如何更充分地利用 score distribution”，实现了 PLBF-style 的 score bucket 与 per-bucket backup Bloom Filter memory allocation。

在最新版本中，我们进一步将 scorer 从 ridge/logistic 改为轻量级 LightGBM tree，记为：

```text
LightTree-PLBF
```

该方法保留 PLBF 的 bucket-specific backup BF 与 DP memory allocation，同时使用小型 tree scorer 捕捉 URL raw feature 中的非线性结构。为了缓解 validation/query distribution mismatch，我们新增 query-like validation split：从真实 query negative 中拆出一部分作为 validation，用于 DP 学习更接近实际 query 的 bucket 权重。

5 个不同 seed 的实验结果显示，LightTree-PLBF 在 128 KiB 及以上稳定超过老师 G-LBF；64 KiB 仍落后，主要原因是 LightTree 模型本身占用一定内存，低内存档位留给 bucket BF 的空间不足。

## 1. 背景与问题

Bloom Filter 是一种经典概率型集合成员查询结构：

```text
优点：空间效率高、查询速度快、无假阴性
缺点：存在假阳性，且 FPR 强依赖内存大小
```

Learned Bloom Filter 的核心思想是使用学习模型作为前置过滤器：

```text
query key
  -> model score
  -> score >= threshold: accept
  -> score < threshold: query backup BF
```

为了保证无假阴性，所有被模型拒绝的正样本必须插入 backup Bloom Filter。

老师的 Gama-LBF 在此基础上进一步优化：

```text
learning model size
threshold
backup BF memory
boosting rounds
```

目标是在固定总内存下最小化整体 FPR。

本项目的目标是：在老师 Gama-LBF 的实验环境下，设计一个更轻量、构建更快，同时尽可能接近甚至超过 G-LBF FPR 的学生模型。

## 3. 方法演进

### 3.1 Hash-based PiecewiseLinearLBF

最早的学生模型直接对 key 做 hash 后进行线性分段回归：

```text
key -> hash -> piecewise linear score -> threshold -> backup BF
```

该方法会破坏 URL/COD 数据中的真实特征结构，模型几乎学不到有效分布。

### 3.2 FeaturePiecewiseLinearLBF

之后改为 feature-aware 版本：

```text
raw features
  -> linear projection
  -> piecewise calibration
  -> threshold
  -> backup BF
```

backup BF 仍存储原始 key，以保证成员查询语义；学习模型只负责预测样本是否更像正样本。

### 3.3 LogisticFeaturePiecewiseLinearLBF

进一步将 ridge projection 替换为 logistic regression：

```text
raw features
  -> LogisticRegression score
  -> piecewise calibration
  -> threshold
  -> backup BF
```

Logistic 版本在部分内存档位优于 ridge，但仍没有追上 G-LBF。

### 3.4 Raw-PLBF-Student

随后引入 PLBF-style 结构，不再使用一个全局 threshold 和一个全局 backup BF，而是将 score 分成多个 bucket，并为每个 bucket 单独分配 backup Bloom Filter 内存：

```text
raw features
  -> ridge/logistic score
  -> score buckets
  -> per-bucket positive/negative density estimation
  -> DP memory allocation
  -> bucket-specific backup BF query
```

该结构的重要变化是：

```text
单阈值 LBF：只判断 score 是否超过 threshold
PLBF：按 score 区间分别估计风险，并分别分配内存
```

这使模型能更充分地利用 score distribution。

### 3.5 LightTree-PLBF

最新版本将 scorer 改为轻量级 LightGBM tree，但保留 PLBF 结构：

```text
raw features
  -> small LightGBM tree scorer
  -> score buckets
  -> per-bucket positive/negative count
  -> DP memory allocation
  -> bucket-specific backup BF
```

实验配置：

```text
tree_rounds = 8
tree_leaves = 8
tree_depth = 3
step_bits = 1024
bucket_counts = 16, 32, 64
C / reg_lambda = 0.1, 1, 10
```

LightTree 的优势在于它可以学习 URL raw feature 中的非线性组合关系。例如 URL 长度、数字比例、特殊字符、host/path/query 结构之间的交互，线性 ridge/logistic 很难表达，而小型树模型可以通过分裂条件捕捉这些模式。

```text
192 KiB: 0.629% -> 0.349%
256 KiB: 0.230% -> 0.102%
320 KiB: 0.092% -> 0.023%
```

但 64/128/192/256 KiB 仍然没有全面超过 G-LBF。

## 6. Bad Bucket Diagnostics

对 Raw-PLBF-Student 做 per-bucket 误报归因后发现，误报集中在少数中高 score bucket：

```text
bucket=17 score=[0.771189,0.791559) pos=7388 query_neg=803 bits=12288 fp=411 bucket_fpr=51.18%
bucket=14 score=[0.631277,0.701246) pos=7305 query_neg=1161 bits=18432 fp=368 bucket_fpr=31.70%
bucket=18 score=[0.791559,0.811353) pos=7467 query_neg=629 bits=10240 fp=350 bucket_fpr=55.64%
bucket=20 score=[0.831405,0.851582) pos=7625 query_neg=315 bits=0 fp=315 bucket_fpr=100.0%
```

这说明两个问题：

```text
1. 某些 bucket 中 positive count 很高，bits_per_positive 不足。
2. 某些高 score bucket 在 validation negative 中很少出现，DP 给了 0 bits，但 query 中仍然出现负样本，导致 FP 爆发。
```

第二点就是 validation/query distribution mismatch：

```text
系统优化的是 validation FPR，
但最终关心的是 real query FPR。
```

## 7. Query-like Validation Split

为缓解 validation/query distribution mismatch，我们新增：

```text
--validation-mode query_split
```

该模式会从真实 `url_query.csv` 的 negative 样本中随机拆分：

```text
50% query negative -> validation negative for DP
50% query negative -> final query evaluation
```

这样 DP 看到的 bucket negative distribution 更接近最终 query distribution，同时避免直接在同一批 query 上调参和测试。

对照实验显示：只把 ridge 模型换成 query_split，并不能带来决定性提升。

| Method | 64 KiB | 128 KiB | 192 KiB |
|---|---:|---:|---:|
| ridge PLBF + query_split | 7.131% | 1.371% | 0.377% |

这说明 query-like validation 有助于估计更稳定，但主要性能提升仍需要更强 scorer。

## 9. 为什么 LightTree-PLBF 会更低

LightTree-PLBF 变强主要来自三个原因。

第一，LightTree scorer 比 ridge/logistic 更适合 URL 特征：

```text
ridge/logistic: 线性边界
LightTree: 非线性分裂 + 特征组合
```

URL 特征中存在很多非线性模式，小树可以更好地区分正负样本，使 score distribution 更干净。

第二，PLBF 比单阈值 LBF 更充分利用 score：

```text
single-threshold LBF:
  一个 threshold
  一个 backup BF

PLBF:
  多个 score bucket
  每个 bucket 独立估计风险
  每个 bucket 独立分配 BF bits
```

因此额外内存可以投给真正容易误报的 bucket。

第三，query_split 让 DP 学到更接近真实 query 的 bucket 权重：

```text
sample validation:
  validation negative 和 query negative 可能不一致

query-like validation:
  DP 直接从 query-like negative distribution 估计 bucket risk
```

这使 estimated FPR 和 real query FPR 更接近。

## 10. Same Scorer Ablation：为什么同样的树，单阈值 LBF 仍不如 PLBF

为了回答一个关键问题：

```text
如果使用同样的 LightTree scorer，
为什么 single-threshold LBF 仍然达不到 LightTree-PLBF 的效果？
```

我们新增了对照脚本：

```text
compare_lighttree_lbf_plbf.py
```

该脚本固定同一类 scorer：

```text
LightTree:
    tree_rounds = 8
    tree_leaves = 8
    tree_depth = 3
    C / reg_lambda = 10
```

然后比较两种结构：

```text
single_lbf:
    LightTree score
    -> one global threshold
    -> one global backup BF

plbf:
    LightTree score
    -> score buckets
    -> per-bucket BF
    -> DP memory allocation
```

注意：这里的 `single_lbf` 是单阈值结构对照，不等同于老师完整 Gama 代码，但它用于隔离“同一 scorer 下结构差异”的影响。

### 10.1 Standard Sample Validation

首先使用标准 sample validation，不使用 query split：

```powershell
python .\compare_lighttree_lbf_plbf.py `
  --memory-kib 64 128 192 256 320 `
  --validation-mode sample `
  --seed 42 `
  --c-value 10 `
  --bucket-count 32 `
  --step-bits 1024 `
  --tree-rounds 8 `
  --tree-leaves 8 `
  --tree-depth 3
```

结果：

| Memory | Same-tree Single LBF | Same-tree PLBF |
|---:|---:|---:|
| 64 KiB | 8.702% | 7.155% |
| 128 KiB | 1.467% | 0.826% |
| 192 KiB | 0.204% | 0.118% |
| 256 KiB | 0.050% | 0.033% |
| 320 KiB | 0.030% | 0.018% |

这说明即使不使用 query-aware calibration，PLBF 结构本身也明显优于 single-threshold LBF。

### 10.2 Query-aware Calibration

再使用 query split：

```powershell
python .\compare_lighttree_lbf_plbf.py `
  --memory-kib 64 128 192 256 320 `
  --validation-mode query_split `
  --seed 42 `
  --c-value 10 `
  --bucket-count 32 `
  --step-bits 1024 `
  --tree-rounds 8 `
  --tree-leaves 8 `
  --tree-depth 3
```

结果：

| Memory | Query-aware Single LBF | Query-aware PLBF |
|---:|---:|---:|
| 64 KiB | 8.933% | 7.253% |
| 128 KiB | 1.418% | 0.842% |
| 192 KiB | 0.201% | 0.108% |
| 256 KiB | 0.063% | 0.035% |
| 320 KiB | 0.030% | 0.016% |

结论仍然一致：

```text
同样使用 LightTree scorer，
PLBF 明显优于 single-threshold LBF。
```

因此，LightTree-PLBF 的优势不是单纯来自“换了一棵树”，而是来自：

```text
1. LightTree 让 score distribution 更有区分度；
2. PLBF 把 score distribution 分桶利用；
3. DP 将 BF bits 精确投给高风险 bucket。
```

single-threshold LBF 即使使用同一棵树，也只能做：

```text
score >= threshold:
    accept
else:
    one global backup BF
```

它无法区分不同 score 区间的 positive density 和 query negative density。

PLBF 则优化：

```text
sum over buckets:
    query_neg_weight_i * BF_FPR(bits_i, positive_count_i)
```

所以它能把内存投给真正影响 FPR 的 score 区间。

这正是老师 Gama-LBF 和当前 LightTree-PLBF 的核心结构差异：

```text
Gama-LBF:
    global threshold + global backup BF

LightTree-PLBF:
    bucket-level risk estimation + bucket-level memory allocation
```

### 10.3 关于 Query-aware Gama 对照的修正

这里需要特别修正一个实验命名问题。

前面新增的脚本：

```text
compare_query_aware_single_lbf_plbf.py
```

最初被命名为：

```text
Query-aware Gama-like LBF vs Query-aware PLBF
```

但严格来说，这个命名不准确。

它实现的是一个简化版 same-scorer single-threshold LBF 消融：

```text
small LightTree scorer
  -> global threshold search
  -> one global backup BF
```

它不是老师原始 Gama。

老师文档和原始脚本中的 Gama 至少包含以下关键机制：

```text
1. 使用真实 score 作为候选 threshold，而不是粗粒度阈值。
2. 用排序 + 滑动统计把 threshold search 从 O(n^2) 降到 O(n log n)。
3. 搜索 LightGBM boosting epoch，也就是同时优化模型大小和 backup BF 内存。
4. 通过历史模型复用避免重复训练。
5. 在 Gama-LBF 之外，老师仓库还包含 Gama-PLBF，对 PLBF 结构也做了 Gama-style 优化。
```

因此，原先那个错误命名的 `compare_query_aware_gama_plbf.py` 不能用来声称：

```text
Query-aware LightTree-PLBF 一定强于老师 Gama。
```

它只能说明一个更窄的问题：

```text
在同一小型 LightTree scorer 下，
PLBF 的 bucket-level memory allocation
优于一个简化 single-threshold LBF baseline。
```

也就是说，它是结构消融，不是老师 Gama 复现。

这个消融仍然有价值，因为它隔离了：

```text
single global threshold
vs
bucket-level BF allocation
```

但文档中不能把它写成“Query-aware Gama-LBF”。

|---:|---:|---:|

结论：


但这个实验不能替代以下真正公平对照：

```text

vs

vs

```

如果要真正证明“不是只因为用了 query distribution”，下一步应该改老师原始脚本，而不是用简化 baseline：

```text

2. 保留老师 Gama 的 epoch/model-size search。
```

这样得到的结果才可以称为：


### 10.5 真正的 Query-aware Teacher Gama 对照

根据老师原始代码，我们进一步新增真正的 query-aware teacher Gama wrapper：

```text
teacher_query_aware_gama.py
```

该脚本保留老师 Gama 的核心逻辑：

```text
Gama-LBF:
    LightGBM boosting epoch search
    true-score threshold search
    model size / backup BF memory trade-off

Gama-PLBF:
    LightGBM boosting epoch search
    FastPLBF_M bucket/region optimization
    model size / PLBF backup memory trade-off
```

唯一变化是 validation 数据来源：

```text
query negative
  -> 50% calibration negative
  -> 50% held-out evaluation negative
```

其中 calibration negative 用于估计 query distribution，held-out evaluation negative 只用于最终测试。注意 threshold / PLBF 优化还需要 positive distribution，因此脚本使用 train+test 的全部 positive 来估计 backup BF 插入量。

运行命令：

```powershell

  --memory-kib 64 128 192 256 320 `
  --methods lbf plbf `
  --epoch-max 200 `
  --seed 42 `
  --calibration-fraction 0.5 `
  --segments 50 `
  --regions 5
```

| 192 KiB | 0.190% |
| 256 KiB | 0.056% |
| 320 KiB | 0.035% |

Query-aware teacher Gama-PLBF 结果：

| Memory | Query-aware teacher Gama-PLBF |
|---:|---:|
| 64 KiB | 4.649% |
| 128 KiB | 0.461% |
| 192 KiB | 0.112% |
| 256 KiB | 0.042% |
| 320 KiB | 0.023% |

和我们当前 seed=42 的 Query-aware LightTree-PLBF 对比：

| Memory | Teacher Gama-LBF | Teacher Gama-PLBF | LightTree-PLBF |
|---:|---:|---:|---:|
| 64 KiB | 5.545% | 4.649% | 7.253% |

这个结果非常重要，它修正了之前的判断：



```text

192 KiB: 40.1s
256 KiB: 59.0s
320 KiB: 76.3s
```

而 LightTree-PLBF 通常约为：

```text
0.7s - 1.5s
```

因此，当前最稳妥的说法不是“全面超过老师 Gama”，而是：

```text
LightTree-PLBF 在高内存档位取得更低 FPR，
并且构建时间显著低于 teacher Gama-PLBF；
但在低内存档位，teacher Gama-PLBF 仍然更强。
```

## 11. 为什么 64 KiB 仍然落后

64 KiB 下 LightTree-PLBF 仍不如老师 Gama-LBF / Gama-PLBF：

```text
teacher Gama-LBF: 5.545% - 5.579%
teacher Gama-PLBF: 4.649%
LightTree-PLBF: 7.085% ± 0.027%
```

主要原因是模型内存开销。

LightTree 虽然很小，但仍比 ridge/logistic scorer 大很多。64 KiB 总预算下，tree model bits、bucket metadata bits 会挤占 backup BF bits，导致 per-bucket BF 空间不足。此时 scorer 变强带来的收益，被 backup BF 空间减少部分抵消。

128 KiB 以后，总内存变宽，LightTree scorer 的非线性优势开始释放，PLBF 也有足够 bits 给坏桶补救，因此 FPR 明显下降。

## 12. 当前最终结论

当前项目最重要的结论是：

```text
单阈值 Student-LBF 不足以追上 Gama-LBF。
PLBF-style bucket-specific BF 是正确方向。
LightTree scorer + PLBF 可以在中高内存档位超过 teacher Gama-LBF。
与 teacher Gama-PLBF 相比，LightTree-PLBF 在 64/128 KiB 落后，在 192 KiB 接近，在 256/320 KiB 更低且快很多。
64 KiB 的瓶颈是模型内存占比过高和低内存下 bucket BF bits 不足。
```

目前最佳方法是：

```text
LightTree-PLBF
  = small LightGBM scorer
  + score bucket partition
  + DP per-bucket memory allocation
  + query-like validation split
```

它的优势是：

```text
1. FPR 在中高内存档位优于 teacher Gama-LBF。
2. 在 256/320 KiB 上优于 teacher Gama-PLBF。
3. 构建时间约 0.7s - 1.5s，明显低于 teacher Gama-PLBF。
4. 5-seed 结果稳定，不是单次偶然。
```

## 13. 增量式 LightTree-PLBF 尝试

老师进一步提出了一个更接近真实系统的问题：

```text
当集合数据发生变化，尤其是有新 key 插入时，
是否必须重新训练模型、重新划分 bucket、重新分配 BF 内存？
```

朴素做法是 full rebuild：

```text
new data
  -> retrain LightTree scorer
  -> recompute scores
  -> rebuild bucket boundaries
  -> rerun DP memory allocation
  -> rebuild all bucket BFs
```

这种方式 FPR 最稳，但 update time 高。

因此我们新增一个增量实验脚本：

```text
incremental_lighttree_plbf.py
```

目标是验证：

```text
能否复用旧 scorer 和稳定 bucket，
只更新受插入影响的 bucket，
从而接近 full rebuild 的 FPR，
同时显著降低 update time。
```

### 13.1 增量结构

增量版将 LightTree-PLBF 拆成：

```text
base LightTree scorer
base bucket boundaries
base bucket BFs
reserved memory
incremental update layer
```

新插入 positive 到来时，不立即重训模型，而是：

```text
new positive keys
  -> old LightTree scorer
  -> existing bucket boundaries
  -> affected buckets
  -> update only affected bucket BFs
```

当前实现了两种增量策略。

第一种是 delta BF layer：

```text
base bucket BF + delta bucket BF
```

它最快，但由于 base BF 和 delta BF 同时参与查询，FPR 会叠加，低内存下效果较差。

第二种是 local bucket rebuild：

```text
affected bucket:
    old keys + inserted keys
    -> rebuild this bucket BF only

unaffected bucket:
    keep unchanged
```

这相当于只对 dirty buckets 做局部重构，而不是全量重训。

### 13.2 实验设置

本轮模拟插入：

```text
insert_fraction = 5%
reserve_fraction = 5%
tree_rounds = 8
tree_leaves = 8
tree_depth = 3
bucket_count = 32
step_bits = 1024
```

对比方法：

```text
base_no_update:
    不处理插入，只用旧模型旧 BF。

incremental_delta:
    新插入 key 放入 delta BF。

incremental_local_rebuild:
    复用旧 scorer 和旧 bucket，只重建受影响 bucket。

full_rebuild:
    重新训练 LightTree，并重建完整 PLBF。
```

评估指标：

```text
query FPR
insert FNR
update / rebuild time
```

其中 insert FNR 表示新插入 positive 是否能被正确查询到。若 insert FNR > 0，说明违反 Bloom Filter 无假阴性的基本要求。

### 13.3 单次实验结果

在 seed=42、5% 插入下：

| Memory | Method | FPR | Insert FNR | Time |
|---:|---|---:|---:|---:|
| 64 KiB | incremental_local_rebuild | 7.365% | 0 | 0.148s |
| 64 KiB | full_rebuild | 7.253% | 0 | 0.689s |
| 128 KiB | incremental_local_rebuild | 0.866% | 0 | 0.248s |
| 128 KiB | full_rebuild | 0.842% | 0 | 0.839s |
| 192 KiB | incremental_local_rebuild | 0.117% | 0 | 0.315s |
| 192 KiB | full_rebuild | 0.108% | 0 | 0.961s |
| 256 KiB | incremental_local_rebuild | 0.035% | 0 | 0.411s |
| 256 KiB | full_rebuild | 0.035% | 0 | 1.132s |
| 320 KiB | incremental_local_rebuild | 0.014% | 0 | 0.569s |
| 320 KiB | full_rebuild | 0.016% | 0 | 1.314s |

可以看到，local rebuild 在保证新插入 positive 无假阴性的同时，FPR 基本接近 full rebuild，但更新时间明显更低。

### 13.4 5-seed 稳定性结果

进一步使用 seed=1..5 重复实验，得到 mean 结果：

| Memory | Local Rebuild FPR | Full Rebuild FPR | FPR Gap | Local Time | Full Time | Speedup |
|---:|---:|---:|---:|---:|---:|---:|
| 64 KiB | 7.295% | 7.085% | +0.210% | 0.271s | 1.129s | 4.16x |
| 128 KiB | 0.852% | 0.802% | +0.050% | 0.360s | 1.091s | 3.03x |
| 192 KiB | 0.112% | 0.100% | +0.012% | 0.546s | 1.562s | 2.86x |
| 256 KiB | 0.034% | 0.038% | -0.004% | 0.725s | 1.796s | 2.48x |
| 320 KiB | 0.012% | 0.018% | -0.006% | 0.749s | 1.712s | 2.29x |

所有 seed 中，incremental_local_rebuild 的 insert FNR 均为 0。

这说明：

```text
局部重构可以在接近 full rebuild FPR 的情况下，
将更新开销降低到 full rebuild 的约 24% - 44%。
```

### 13.5 论文性创新点

这个方向可以总结为：

```text
Drift-Aware Incremental LightTree-PLBF
```

核心思想是：

```text
不要把数据变化看成必须全量重训的问题，
而是把变化定位到 score bucket 层面。
```

当新数据到来时：

```text
small update:
    delta BF layer

medium update:
    local bucket rebuild

large drift:
    full rebuild
```

这形成了一个三级持续学习 / 增量维护框架。

它的论文性贡献可以表述为：

```text
We propose an incremental maintenance strategy for PLBF that reuses the learned scorer
and stable score buckets, while rebuilding only drift-affected bucket Bloom filters.
This achieves near-rebuild FPR with substantially lower update time.
```

中文表述：

```text
我们提出一种面向数据变化的增量式 PLBF 维护机制。
该方法复用稳定的 LightTree scorer 与 score bucket，
仅对受插入影响的 bucket 进行局部 BF 重构，
在接近全量重构 FPR 的同时显著降低更新时间。
```

## 14. 后续优化方向

后续最值得尝试的方向如下。

### 14.1 64 KiB 专用 ultra-light tree

64 KiB 的核心问题是模型占用太多 bits。可以尝试：

```text
tree_rounds = 2, 4, 6
tree_leaves = 4
tree_depth = 2
```

目标是牺牲少量 scorer 表达能力，换取更多 backup BF bits。

### 14.2 Seed-averaged final table

当前已经完成 5-seed query_split。若要写进正式报告，可以进一步固定实验格式：

```text
mean ± std
construction time mean ± std
best config frequency
```

### 14.3 Bucket lower-bound allocation

bad bucket 中仍存在少数 query negative 出现但 validation 权重较低的情况。可以尝试给每个非空 positive bucket 一个最小 bit allocation：

```text
min_bits_per_nonempty_bucket
```

避免 DP 因 validation negative 过少而给某些 bucket 分配 0 bits。

### 14.4 Smaller metadata assumption

当前脚本中 metadata bits 使用简单估计：

```text
metadata_bits = bucket_count * 128
```

后续可以更精确估算 bucket boundary 和 allocation table 的存储成本，避免对学生模型过度惩罚或过度乐观。

### 14.5 Drift trigger policy

当前增量实验默认插入后直接 local rebuild affected buckets。后续可以加入 drift trigger：

```text
if delta_size_i is small:
    use delta BF only
elif bucket estimated FPR increases:
    local rebuild bucket
else:
    full rebuild
```

这样可以把增量维护从实验脚本推进成完整算法。

## 15. 一句话总结

本项目最终从“调一个更好的 threshold”推进到了“设计一个更好的 Learned Bloom Filter 结构”：

```text
LightTree 负责产生更有区分度的 score；
PLBF 负责按 score distribution 精细使用内存；
query-like validation 负责让 DP 优化目标更接近真实 query。
```

因此，LightTree-PLBF 在 128 KiB 及以上稳定超过老师 G-LBF，是当前最有说服力的结果。
