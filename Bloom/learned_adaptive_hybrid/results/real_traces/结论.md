# 第二条真实轨迹：MAWI（WIDE 骨干网）2020-04-08（2026-10-28）

数据准备：`src/prepare_mawi.py`。各方法的结果分别写在 `results/exp10_baselines` 到 `results/exp14_warm_controller` 下的 `rows_mawi2020_flow*.json`，口径和其余实验完全相同。

## 为什么选 MAWI

- **可选范围有限。** CAIDA 其他时段的数据要签使用协议才能下载，我们手上只有 How to Train Your Filter 仓库里那一份 Caida。
- **MAWI 能公开下载，满足三个条件**：
  1. 有成员集合：沿用 Caida 的定义，UDP 流是成员，TCP 流是非成员；
  2. 查询里有大量非成员：TCP 包占 84%；
  3. key 有可学的特征：地址（已做前缀保持的匿名化）和包长。
- **它和 Caida 是不同的观测点**（日本的 WIDE 骨干网），**也是不同的年份**（2020 年，Caida 那份是 2016 年）。处理流程与 caida_flow 完全一样，规则和各方法都没有调参。

## 数据处理

- 取当天 15 分钟轨迹的前 1000 万个包（约 1.4 分钟的流量）。只保留 TCP/UDP，共 731 万个包，其中 UDP 117 万个。
- 按（源，目的，协议）聚成流：成员 7.6 万条 UDP 流，测试查询池 41.6 万条 TCP 流。
- 查询轨迹是测试池里 TCP 流的包，按时间顺序排列，共 578 万次查询，不同 key 只占 7.2%。
- **修正过一处特征口径**：tcpdump `-q` 输出的是净载荷长度，TCP 纯 ACK 是 0，"出现 0 长度"几乎就等于"这是 TCP 流"。已统一换算成 IP 包总长（和 Caida 同口径），TCP 加 40 字节、UDP 加 28 字节，IPv6 再各加 20 字节。

## 这条轨迹的性质：模型几乎没有误报可修

即使换算了包长，TCP 流和 UDP 流仍然很好区分。Gama 只选 1 棵树，40KiB 下验证集估计 FPR 也只有 0.014%。所以这条轨迹主要检验两件事：
- **不退化**：模型已经很准时，加缓存会不会反而变差；
- **剩余收益**：少量误报 key 被反复查询时，缓存还能不能带来收益。

- Gama＋缓存在每个预算下都是最好的。它选 1 棵树、8–13% 的缓存，误报约为 Gama 的 1/2.6。

- 绝对数字都很小。这条轨迹说明：模型已经很准时，方法不退化，而且在误报 key 反复出现的地方仍有收益。它不能用来展示"大幅降低误报"。

## 对论文的含义

- **真实轨迹现在有两条**：Caida（2016，流级）和 MAWI（2020，另一个观测点）。在两条上，Gama＋缓存（学习期校准）都不需要调参，都是最好或接近最好。
- **两条轨迹的性质不同**：Caida 上模型误报多，缓存收益大；MAWI 上模型几乎完美，缓存只补剩余的那一点。正好覆盖"有很多可修"和"几乎没得修"两种情况。
- **要如实写明**：MAWI 上绝对误报很少，它支撑的是"不退化"，不是"大幅改善"。要证明"现实中普遍有大量可修误报"，还需要一个误报更多的不同领域的真实轨迹，比如 URL 访问日志配恶意 URL 名单。
