# 第一个验证实验：朴素混合的剩余误报从哪里来（2026-10-27）

脚本：`src/exp1_fp_source.py`（原 `hybrid_fp_source.py`，已拆成 `src/common.py`＋本脚本，重跑 600 行结果逐字段一致）；完整表格：`report.md`；逐次运行：`rows.json`；运行日志：`run.log`；图：`figures/fig1`、`fig2`。

> 后续：三项核对见 `results/checks/checks.md`（adv* 已更名为“探测重放”，属于重复型负载）；下面“需要立刻补的对照”已在实验 2 完成，见 `results/exp2_repetition_cache/结论.md`。

## 设置

- 数据：Kaggle celestialclassify（Gama 原文 COD 来源），共 600 万行；300 万 galaxy 作为成员，300 万 star 作为非成员。按 objID 哈希划分：训练负例 160 万，验证负例 40 万（PLBF 用它估计分段负例分布），测试负例 99.96 万（所有查询负载都从这里取）。
- 模型：本机重新训练的 LightGBM，48 树，31 叶，49 个数值特征，用 200 万成员加 160 万负例训练；模型内存按原研究口径记为 48×700B。**这不是 Windows 上那个 48 树模型**，数据预处理也没有对齐。
- 结构（内存相同，模型内存计入预算）：
  - BF：纯 Bloom Filter。
  - AQF：AdaptiveQF 的抽象实现。指纹 = h1 mod (槽数·2^r)；每槽 r+3 bit，负载 0.95，另外预留 5% 槽位给扩展用，预留槽也计入内存。发生误报时，把冲突成员的指纹扩展 r bit，直到它和这个查询不再冲突。没有计入反向映射的查询成本。
  - PLBF：100 个分位数分段，每段单独分配 FPR（拉格朗日二分，再用贪心补满预算）。分配结果为 FPR=1 的段就是"模型直接放行"。
  - PLBF+AQF：同一模型、同一分段，backup 换成 AQF，按 AQF 的空间代价重新分配。
- 负载：每次 1000 万条非成员查询，10 个种子。uniform、Zipf 1.0、Zipf 1.5、天区漂移（按 ra 排序，用 5 万个 key 的窗口滑过整个查询池），以及 2%/10% 自适应对抗（对抗者记住已经出现过的误报并反复重放，被修正后丢掉）。
- zero-FN：构建时检查了全部 300 万成员。

## 结论

**难点 2 成立，但只在低内存区间成立；而且最简单的修正办法可能已经够用，需要尽快验证。**

1. 256KiB 和 1MiB（每个成员 0.7–2.8 bit）下，朴素混合剩下的误报有 **90–96%（均匀、漂移）、72–97%（Zipf）、99–100%（对抗）** 来自模型直接放行。对抗 10% 时 FPR 是 9.6% 和 8.9%，和纯 PLBF（9.5% / 9.0%）几乎一样。也就是说，把 backup 换成 AQF 在对抗负载下基本没有作用。如果直接放行区的误报能全部修掉，256KiB 下 FPR 可以从 0.635% 降到 0.029%，对抗下从 9.6% 降到 0.029%。
2. 在这个区间，**纯 AQF 根本放不下**：每个成员至少要约 4.2 bit，300 万成员在 256KiB 和 1MiB 下都不可行。所以"直接用 adaptive filter"这条路，在 learned filter 有优势的内存区间并不存在。
3. 4MiB（每个成员 11 bit）下，PLBF+AQF 几乎没有直接放行区（只剩 1 段）。所有负载下误报都是 0，包括对抗负载；纯 AQF 是 0.073%。**高内存时朴素混合已经够好，没什么可做的。**（更正：初版写的"纯 PLBF 在对抗 10% 下是 7.9%"来自 BF 双重哈希的缺陷，修复后纯 PLBF 在 4MiB 下也是 0 误报，见 `docs/决策记录.md`。本文其余数字修复后重跑，变化在种子波动范围内。）
4. 256KiB 均匀负载下，朴素混合（0.635%）反而比 PLBF（0.565%）差。原因是 AQF 在低 bit 时每个成员的固定开销大，分配器只好把更多段改成直接放行：测试负例落在直接放行区的比例从 0.16% 涨到 0.61%。混合结构的内存分配本身就是问题的一部分。
5. 天区漂移对模型几乎没有影响，FPR 和 uniform 一样。这种漂移没有给 learned filter 施压。往"难负例"方向漂移的场景没有测。

## 需要立刻补的对照（决定这个方向是否只是"加个缓存"）

在直接放行区里，会误报的测试负例 key 数量：256KiB 下 PLBF 是 1,618 个，PLBF+AQF 是 6,062 个；1MiB 下只有 14 个和 80 个。即使存精确的 32 bit 指纹，6,062 个 key 也只要约 24KB。对这个大小的查询池来说，**一个从预算里扣出来的负例缓存（Adapt or Cache? 那篇的思路）可能就足以修掉大部分误报。**

要注意，这个实验的查询池只有 100 万个 key，每个 key 平均被查询 10 次，这对 adaptive 和 cache 都有利。真实场景中非成员的全集大得多，查询会持续触到没见过的高分非成员。

所以下一步应该是：

- 增加一个 PLBF + 负例缓存的对照组（缓存容量从预算里扣，LRU 或 FIFO），和朴素混合、理想上界（直接放行的误报全部消除）放在一起比。
- 把查询池扩大到全部 300 万非成员，并加入"重复率低"的负载，比如每个 key 只查询 1–2 次。
- 加一个往难负例漂移的负载：窗口按模型分数从低往高滑。

如果负例缓存在低重复率和对抗负载下都接近理想上界，论文主线就会退化成"learned filter 加一个缓存"，需要重新判断。如果缓存在低重复率下失效，或者容量和 backup 抢内存的问题很难平衡，那么"在模型、adaptive 结构、负例修正结构之间联合分配内存"就是一个站得住的技术核心。
