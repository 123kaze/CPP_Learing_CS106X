# 实验 3：Caida 上误报工作集远大于缓存的情形（2026-10-27）

脚本与实验 2 相同（`src/exp2_repetition_cache.py`，参数见 `README.md`）。表格见 `report.md`，图见 `figures/fig6`、`fig7`。

## 为什么用 Caida

实验 2（COD）中，误报工作集被查询池的大小封顶：最多约 5,700 个 key，约 20KB，相当于 256KiB 预算的 8%，所以一个固定比例就够用。要检验"工作集远超缓存"的情形，需要负例全集大的数据。

Caida 来自 How to Train Your Filter 的 benchmark 仓库，取的是论文用的同一份预处理数据：
- key 是包序号 `No.`；
- 特征是 Time、Source、Destination、Length；
- UDP 包 119.6 万个作成员，TCP 包 729.8 万个作非成员。

按 key 哈希切分负例：训练 10%、验证 10%、测试 80%（583.8 万个，所有查询都从这里取）。模型同样是 LightGBM 48 树。

256KiB 下，纯 PLBF 对全部测试负例的静态误报 key 约 11.3 万个（4.5 万在直接放行区，6.8 万在 backup），每条按 27.5 bit 算，全部缓存下来需要约 389KB：是整个预算的 1.5 倍，是 10% 缓存（26KB）的 15 倍。

## 设置

- 预算：128KiB、256KiB、1MiB，对应每成员 0.88、1.75、7.0 bit。
- 缓存比例：0/1/2/5/10/20/40%。
- 查询池：1 万、10 万、100 万、全部（583.8 万），每个池子配 {均匀, Zipf 0.8/1.1/1.5} 四种分布。
- 另外四种负载与实验 2 相同：每 key 一次、全新对抗、向难负例漂移、探测重放 10%。
- 5 个种子取均值。

## 结果

1. **低预算下，最优缓存比例的变化范围大得多。** 128KiB 和 256KiB 下，不同负载的最优比例覆盖了网格里的全部 7 档（0% 到 40%）。COD 上只在 0–10% 之间变化。
2. **最好的固定比例本身随数据集和预算变化，而且仍有可观的代价。**

   | 数据集 | 预算 | 最好的固定比例 | 它在最差负载上的代价 |
   |---|---|---:|---:|
   | COD | 256KiB | 10% | 1.27× |
   | COD | 1MiB | 5% | 1.22× |
   | Caida | 128KiB | 20% | 1.33× |
   | Caida | 256KiB | 40% | 1.75× |
   | Caida | 1MiB | 2% | 1.16× |

   照搬一个默认值的代价可能很大。比如在 COD 上表现很好的 10%，放到 Caida 128KiB 最差会差 14 倍（10 万 key 池的均匀负载），放到 Caida 256KiB 最差会差 3.8 倍（难负例漂移）。（图 6）
3. **工作集远大于缓存时，最好的缓存离下界也有明显距离。** Caida 128KiB 和 256KiB 下，网格里最好的比例与无限免费缓存的比值，中位数是 1.23 和 1.08，但最大到 10.0 和 5.4。差距大的是"100 万池均匀""全部池 Zipf 0.8"和"向难负例漂移"这类负载，误报 key 的出现次数分布很散。在图 7 上，这些点明显高于对角线。
4. **1MiB 下又回到实验 2 的情形。** 工作集很小（全部测试负例中静态误报 key 约 6.5 千个），固定 2% 在所有负载上最差只差 1.16×，与下界的比值最大 1.08。
5. **朴素混合 PLBF+AQF 在 Caida 上依旧最差或接近最差。** 全新对抗下所有结构仍然失效：128KiB 下全是 100%，256KiB 下 91–100%。
6. **全部测试负例上的均匀负载里，不加缓存最好。** 1000 万次查询分摊到 583.8 万个 key，每个 key 平均只出现 1.7 次，缓存收益抵不过它挤占的内存。

## 对照决策表

| 结果 | 本次是否出现 |
|---|---|
| 缓存在所有负载下都接近理想上界 | **只在工作集小的设置下成立**（Caida 1MiB、COD）。Caida 128/256KiB 下最差离下界 5–10 倍 |
| 缓存和 backup 抢内存，固定比例怎么调都明显不如最优分配 | **部分出现**。最优比例从 0% 到 40% 都有，选对的固定比例最差也要差 1.33–1.75 倍，而且最好的固定比例本身随数据集和预算变化（2%–40%） |
| 全新对抗负载下所有结构都失效 | **是** |

## 含义

- "加一个负例缓存"这个机制本身仍然不新，第一行的判断不变。
- 但"缓存该占多少内存"在工作集大、预算紧的区间是一个真问题：
  - 答案取决于负载的重复结构，即会再次出现的误报 key 有多少、出现次数分布有多偏；
  - 选错的代价是几倍到十几倍；
  - 而且没有一个跨数据集通用的默认值。
- 这正是 Gama 那类"按负载在线决定内存分配"的问题。决策所需的信号（误报 key 的再出现率、缓存淘汰后又误报的比例）在运行时可以直接从反馈里统计，不需要额外标签。

## 局限

- 每个设置只有 5 个种子，比例网格是离散的 7 档，"最优比例"有离散化误差。
- 缓存淘汰策略只测了 FIFO。工作集远大于缓存时，换成 LRU 或带准入的策略可能会缩小离下界的差距，这本身可能就是一部分答案。
- Caida 的特征只有 4 列，模型比 COD 弱（256KiB 下 PLBF 的 FPR 约 1.9%，COD 是 0.55%）。
