# 实验 8：上限的模型推导，与用 HLL 在线估计 N_eff（2026-10-27）

脚本：`src/exp8_cap_and_neff.py`（第 1、2 部分）和 `src/exp8b_model_neff.py`（N_eff 直接代入模型）。表格见 `report.md` 和 `report_b.md`，图见 `figures/fig11`。

## 方法（不拟合任何常数）

对每个缓存比例 f，按以下三步估算误报次数：

1. **p(f)**：预算扣掉缓存后，PLBF 在验证集上的估计 FPR，用的是和实验结构同一个分配器。
2. **k(f)** = f × 预算 ÷ b̄，即缓存能放多少条。
3. 假设误报 key 在热度排名上是随机抽出来的、占比 p(f)，查询服从 Zipf(s)，在生命周期 Q = 1000 万次查询内估算误报次数。缓存模型取两种：
   - TOP-k：TODS 证明的最优静态缓存，并计入每个 key 第一次出现时的误报；
   - Che 近似的 LRU：和实验里实际用的策略一致。

在 s ∈ {0, 0.5, 0.8, 1.1, 1.5} 上取"最坏相对代价最小"的比例。

全过程只用模型、验证集和三个声明的部署参数：偏斜度范围 S、生命周期查询数 Q、负例全集大小 N。因为没有任何从数据里拟合的常数，"留一数据集"检验自动满足。

HLL 用 2048 个寄存器，共 2KB，这部分从缓存预算里扣。它对窗口内不同负 key 数的估计误差：中位数 1.7%，最大 7.3%。

## 结果

1. **N 取全集大小时，模型在"装得下"的设置里和规则一致，但在"装不下"的设置里推出的上限太低。**

   | 设置 | 实验 7 事后最好的上限 | 模型推出（全集 N） | 模型的最坏代价 |
   |---|---:|---:|---:|
   | Caida 128KiB | 30% | 7.5% | 30×（10 万 key 池的均匀负载） |
   | Caida 256KiB | 30% | 6.5% | 8×（难负例漂移） |
   | Shalla 256KiB | 40% | 23% | 25×（10 万 key 池的均匀负载） |

   在装得下的设置里，模型推出的比例和规则几乎一样：COD 256KiB 9.5% 对 9.4%，Caida 1MiB 2.5% 对 2.4%，Shalla 1MiB 19% 对 19%，Shalla 2MiB 2.0% 对 1.7%。

   **装不下时出错的原因**：模型假设查询分散在整个负例全集上（Caida 是 583.8 万个），而最差的那些负载只查一个小的活跃集合，比如 10 万个 key、每个查约 100 次。所以**上限问题本质上是 N 的问题**。事后最好的上限之所以高达 30–40%，就是为了照顾这类活跃集合小的负载。

2. **把 HLL 估出的 N_eff（整个生命周期）代入模型，上限问题基本解决**（实验 8b）。N_eff 向上取整到 2 的四分之一次幂的档位，宁可高估：

   | 设置 | 模型（N_eff）最坏 / 中位数 | 模型（全集 N）最坏 | 事后上限 40% 最坏 / 中位数 |
   |---|---|---:|---|
   | COD 256KiB | 1.30× / 1.03× | 1.35× | 1.37× / 1.19× |
   | COD 1MiB | 3.00× / 1.32×（每百万次查询多 440 次误报） | 1.50× | 1.00× / 1.00× |
   | Caida 128KiB | 1.89× / 1.03× | 31.9× | 1.64× / 1.38× |
   | Caida 256KiB | **7.53×**（难负例漂移） / 1.05× | 8.04× | 1.80× / 1.68× |
   | Caida 1MiB | 1.18× / 1.04× | 1.14× | 1.12× / 1.02× |
   | Shalla 256KiB | 1.24× / 1.02× | 25.0× | 1.30× / 1.12× |
   | Shalla 1MiB | 1.45× / 1.03× | 1.37× | 1.38× / 1.33× |
   | Shalla 2MiB | 1.09× / 1.05× | 1.20× | 1.16× / 1.09× |

   - 中位数代价全部在 1.02–1.05×（COD 1MiB 除外），比事后挑的上限 40% 好。
   - 最坏代价有 6 个设置在 1.9× 以内。
   - **两个例外**：
     - Caida 256KiB 的难负例漂移差 7.5 倍。漂移不是 Zipf 型负载，模型覆盖不到，需要在论文里单独说明。
     - COD 1MiB 差 3 倍，原因是 8b 的比例网格步长 1%，加上 HLL 本身占的 0.2%，到不了最优的 0.05%。不过绝对代价很小，每百万次查询只多 440 次误报；把网格在 0 附近加密就能解决。

3. **N_eff 必须覆盖缓存的整个生命周期，只看前缀会低估。** 只用前 10% 的查询来估 N_eff，在难负例漂移和全池均匀负载上会差 3.5–20 倍，和实验 7 的发现一致：N 估小很危险。

## 一个必须说清楚的限制

8b 的 N_eff 是在整条轨迹上统计、再从一开始就用上的，这等于事先知道了整个生命周期的不同 key 数，带有后见之明。真正在线的控制器只能看过去，有两种可能的做法：

- 根据 HLL 计数随时间的增长曲线，外推到生命周期结束时的 N_eff；
- 定期按最新的 N_eff 重新设定比例。往大调比例时，把 backup 分段改成直接放行就能腾出内存，不需要重建；往小调则要重建分段的 BF，见问题定义注记 5。

这两种做法都还没测。所以目前能写进论文的是：**"给定缓存生命周期内的 N_eff，模型无需拟合常数即可给出比例"**，加上 N_eff 可以用 2KB 的 HLL 精确计数（误差 ≤7.3%）。至于"在线估计 N_eff"，现在还只是方向。

## 对贡献 2 的含义

- 不再需要单独的上限：装得下和装不下两种情形统一成一个模型，只需三个部署参数：偏斜度范围、生命周期查询数 Q、N_eff。
- 这个模型和 Gama、PLBF 的思路一脉相承：都是用"过滤器 FPR 随内存变化的曲线"去权衡另一项收益，只是这里另一项换成了缓存在 Zipf 负载下的命中率。
- 模型覆盖不到的负载（比如漂移）要列为局限。实验里"难负例漂移"的最坏代价是 7.5 倍。

## 局限

- 每种负载 3 个种子；偏斜度范围、Q 都是声明的参数，没有测它们设错时的敏感性。
- Zipf 假设误报 key 和热度无关，而真实系统里热点负例可能更容易落进放行区。难负例漂移就是这种情况的一个极端例子。
