# 问题定义（2026-10-27）

> **在固定内存下，让 learned filter 面对会重复、会漂移的真实查询时，误报不失控，并且始终保持零漏判。**

正文来自 claude.ai 上的讨论稿。凡是和本地实验数据对不上、或者需要加限定条件的地方，都在文末"核对注记"里逐条说明。组会和引言引用时，以注记修正后的说法为准。

## 问题从哪来

learned filter 的空间节省，来自模型直接放行的那块区域：这块区域不存任何东西，所以省内存。代价是这份节省押注在负查询的分布上。真实查询会集中到少数热点，也会随时间漂移。一旦热点负例落进直接放行区，每查一次就误报一次。

Caida 256KiB 下的"向难负例漂移"负载就是一例：纯 PLBF 的 FPR 从均匀负载的 1.94% 涨到 26.5%（注记 1）。

## 为什么现有方法解决不了

| 方法 | 做不到什么 |
|---|---|
| Gama、PLBF、CLBF | 只按一个去重的负样本集合优化，看不到重复，部署之后也不会调整 |
| 定期重训或重建 | 成本太高，B 路线已经把这一点测量清楚了 |
| adaptive filter（AQF） | 低内存下放不下所有成员；接在 learned filter 后面，又修不到模型放行区的误报 |
| 加一个负例缓存 | 机制有效，但缓存该占多少内存取决于负载，选错差几倍到十几倍，而且没有跨数据集通用的默认值 |

最后一行就是论文的切入点：**机制大家都能想到，难的是内存怎么分。**

## 论文贡献（计划中的三点）

1. **刻画什么能修、什么修不了。**
   - 重复型负载下，缓存足够大时，误报次数等于不同误报 key 的个数（注记 2）。
   - 全新对抗查询下，任何低成本方案都做不到，这里有一个下界：要花 n_H·log2(1/ε) bit，相当于把模型在放行区省下的空间全部还回去（注记 3）。
   - 这部分回答了 How to Train Your Filter 公开提出的问题。
2. **轨迹感知的联合内存分配。** 把 Gama 的评估对象从负样本集合换成查询轨迹，在模型、过滤器和缓存之间联合分配内存。原版 Gama 按去重的负样本评估，缓存在这种评估下没有收益，所以等价于选 0% 缓存（注记 4）。
3. **负载漂移时在线调整。** 运行时根据误报反馈调整缓存比例（注记 5）。

| 内容 | 状态 |

| 最优缓存比例随负载变化，选错代价大 | Caida 上已证实；网格补到 60%/80% 后不变，四种淘汰策略下都成立（实验 4） |

## 部署参数

实验 9 之后，误报流模型只需要运行时测得的三个量（Q_F、D_F、前 256 个误报 key 的查询占比），草图约 5KB，计入预算。

下面是实验 7、8 版本的模型需要声明的参数，留作对照：
- **N_eff**：缓存生命周期内会被查到的不同负 key 数，可以用 HLL 计数；**宁可高估**，低估的代价远大于高估；
- **Q**：生命周期内的查询数；
- **偏斜度范围**：Zipf 指数的范围。

漂移这类非 Zipf 型负载不在模型的覆盖范围内。

## 核对注记

1. **"FPR 从 2% 涨到 26%"**：数字核对无误（`results/exp3_caida_working_set`，256KiB，纯 PLBF：均匀、全部池 1.94%，向难负例漂移 26.46%；128KiB 是 4.02% → 28.02%）。但这个漂移负载是我们**合成**的：第 t 条查询以 0.5·t/Q 的概率来自模型分数最高的 2 万个测试负例。写论文时要标明是压力测试，不能当成真实轨迹上观察到的现象。
2. **"误报次数约等于不同误报 key 的个数，和查询总量无关"**：严格说，FP = D_F 只在**缓存无限大**时成立（定理 1a）。D_F 本身会随查询量增长，直到误报 key 被查遍为止，所以"和查询总量无关"要改成"只取决于查询轨迹中不同误报 key 的个数"。缓存有限、工作集又远大于缓存时，这条不成立：Caida 128/256KiB 下，最好的缓存离 D_F 还差 5–10 倍。
3. **下界**：依赖"模型不可区分"这个假设，即在 H 区内，模型分数无法区分成员和非成员（`docs/定理草稿.md` 定理 2）。另外，"把模型在放行区省下的空间全部还回去"是解释性的说法：下界的数值等于在 H 区为 n_H 个成员建一个 FPR 为 ε 的标准过滤器所需的空间。
4. **"原版 Gama 一定会选 0% 缓存"**：Gama 的设计空间里本来就没有缓存。准确的说法是：在 Gama 的评估方式下（每个负样本出现一次），缓存的收益为 0。实验 2/3 的"每 key 一次"负载正好对应这种评估，在所有预算下最优比例都是 0%。
5. **在线调整的成本是不对称的**：
   - **backup → 缓存**：把某个 backup 分段改成直接放行，释放它的 BF 空间，不会产生漏判，也不需要重建。代价是该段的 FPR 变成 1。原稿写的"零成本"只在不计这部分 FPR 时成立。
   - **缓存 → backup**：要为该分段重建 BF，必须重新取得该段的全部成员 key。这正是 B 路线测出的历史回放成本（要读全部成员并重新评分，或者维护按分数组织的索引）。
   - 所以第 3 点的方案必须说明缩回去的路径，或者把调整方向限定为单向，或者只在已有的 compaction / 重建时机执行反向调整。
6. **"两个数据集都已证实"**：COD 见实验 1。Caida 的数据从实验 3 的结果里补算：128/256KiB 下，PLBF+AQF 剩余误报中来自直接放行的比例，在重复型负载上是 83%–100%；在 1MiB、重复少的负载上会降低（每 key 一次 39%，全部池均匀 57%，全新对抗 59%）。所以这一条应限定为"低内存、重复型负载"。

## 待验证实验的设计草案

### A. 差距来自哪里：比例、容量，还是淘汰策略

数据集 Caida，预算 128/256KiB，沿用实验 3 的负载，每个负载比较以下几种结构：

- FIFO 缓存，比例补到 60%、80%（网格向上延伸）；
- LRU 缓存，相同比例网格；
- oracle-LFU：按整条轨迹里每个误报 key 的总出现次数，静态保留次数最多的那些 key，直到占满容量。这一项需要事先知道未来，只作参照；
- OPT（Bélády）：对每个比例，计算离线最优淘汰下的误报次数。条目大小几乎相同（27–29 bit），可以按条数近似，等长条目下 Bélády 是最优的；
- 无限免费缓存，作为下界。

判读：
- 如果 OPT 在最优比例下也离下界很远，差距主要是**容量**造成的，第 2 点会弱化。
- 如果 OPT 或 LRU 贴近下界而 FIFO 不行，差距在**淘汰策略**。
- 只有当 OPT 的最优比例也随负载大幅变化、而且固定比例下 OPT 仍然代价大时，"**比例**"才是主因。

### B. 离线轨迹感知分配在负载错配下的代价

用轨迹 T1 的前一部分作为"训练轨迹"，在比例网格上选出最优缓存比例，再拿这个比例去跑另一条轨迹 T2，记录代价 = FPR(训练选的比例, T2) ÷ FPR(T2 上的最优比例)。

轨迹组合要覆盖三类错配：
- 同族不同参数（Zipf 1.1 → Zipf 0.8）；
- 不同查询池大小（10 万 → 全部）；
- 从平稳到漂移（均匀 → 向难负例漂移）。

如果错配的代价普遍在 1.3× 以内，第 3 点可以去掉。
