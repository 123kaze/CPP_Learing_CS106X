## 2026-10-27 B 路线第一轮：修复 BF 缺陷、校验真实 AQF、Caida、开销、定理草稿

### BF 实现缺陷（已修复，相关结果已重跑）

- **问题**：BF 原先用双重哈希 h1 + j·h2 mod m。在"成员极少、每成员 bit 很多"的分段里（例如 1 个成员、40 bit、28 个哈希），探测位高度相关，实测 FPR 比理想 BF 高几个数量级。这种分段只在预算大时才会出现。
- **修复**：每个探测位改用独立混合（`common.bf_pos`）。修复后，两个数据集在各个预算下的实测 FPR 都和估计值吻合。
- **影响**：
  - 实验 1 中"4MiB 纯 PLBF 在对抗负载下 7.86%"是假象，修复后为 0，已在实验 1 结论和核对文档中更正；
  - 其余结果变化都在种子波动范围内，实验 2 的结论不变；
  - 实验 1、核对、实验 2 均已重跑。

### 抽象 AQF 与作者实现的对照（`results/validate_aqf/`）

- **做法**：把 How-to-Train-Your-Filter 仓库里的 AdaptiveQF（gqf.c）移植到 ARM，放在 `external/aqf_port`。改动只有三类：
  - 把 x86 内联汇编换成编译器内建函数；
  - 去掉 Linux 专用的头文件；
  - 去掉 posix_fallocate。

  驱动程序照搬作者的 aqf_adapter.c。
- **结果**：COD 和 Caida 各 9 组设置，r 取 5/7/9，三种负载。
  - 抽象 FPR ÷ 真实 FPR：中位数 1.002，范围 1.000–1.011；自适应次数基本一致。
  - 真实内存比抽象记账（r+3 bit/槽）多 1.5–2.3%，所以抽象实现让 AQF 多占了约 2% 内存，对 AQF 略有利，结论不变。
  - 移植后在 Caida 上的 AQF 大小与论文仓库列出的预算逐字节一致（2,144,675 B 等）。

### 实验 3：Caida（`results/exp3_caida_working_set/结论.md`）

- 128/256KiB 下误报工作集远大于缓存。不同负载的最优缓存比例从 0% 到 40% 都有。
- 最好的固定比例本身随数据集和预算变化（COD 10%/5%，Caida 20%/40%/2%），选对了最差也要差 1.33–1.75×。照搬 COD 上的 10%，在 Caida 128KiB 最差差 14 倍。
- 工作集大的负载上，最好的缓存离下界仍有 5–10 倍。
- 1MiB 下又回到"固定比例就够"（最差 1.16×）。
- **判断**：机制不新，这一点不变。但在预算紧、工作集大的区间，"缓存占多少"是依赖负载的真问题，选错代价大，也没有通用默认值。决策表第二行部分出现。

### 缓存查询开销（`results/bench_cache_overhead/`）

- 单线程 numba：一次缓存探测约 7 ns，48 树推理 450–540 ns，模型加 PLBF 共 530–610 ns。
- 整条路径加上缓存后变化 −0.6% 到 +4.9%，量级和计时噪声相当；缓存探测本身约占 1.3%。
- 重复型负载下命中的查询直接跳过模型推理，所以缓存反而会提速（此项未单独测）。
- 作为参照，LightGBM 自带的单线程 predict 约 1.1–1.2 µs/条。

### 定理草稿（`docs/定理草稿.md`）

- **上界**：无限缓存时 FP = D_F = D_H + D_{F_B}，取等号；有限 FIFO/LRU 缓存时用 Sleator–Tarjan 的竞争比。
- **下界**：在"模型不可区分"假设下，对全新查询，m ≥ n_H·log2(1/ε) − O(n_H)。
- **引理**：前缀长度 L = log2 n + O(1)，实测在两个数据集上都是 log2 n + 1.3。
- 还没写严格的部分已在文中列出。

## 2026-10-27 实验 4：差距来自比例、容量还是淘汰策略（含 B 预览）

- Caida 128/256KiB，比较 FIFO、LRU、oracle-LFU、OPT 四种淘汰策略，比例网格补到 80%。FIFO 和实验 3 逐行一致。
- **淘汰策略**：在漂移负载上影响最大。256KiB 漂移负载，最优比例下离下界：FIFO 5.39×，LRU 2.94×，OPT 2.10×。**以后默认用 LRU。**
- **容量**：128KiB 下 100 万 key 池的均匀负载，连 OPT 也离下界 6.32×。这类"重复但装不下"的负载应作为刻画的第三种情形。
- **比例**：四种策略下最优比例都在 0–40%（个别 60%）之间变化。每个预算的最佳固定比例最差只差 1.33–1.75×，而且这个结论不依赖淘汰策略。
- **B 预览**（`results/exp5_mismatch`，只用实验 4 的结果，没有新模拟）：
  - 离线按轨迹选比例，在错配下代价很大：平稳 → 漂移在 256KiB 下差 5–10 倍；训练负载选了 0% 而部署负载有重复时，差几百倍。
  - 这比"每个预算一个稳健固定比例"更差。
- **判断**：
  - 贡献 1 扩成三类情形：重复且装得下、重复但装不下、全新。
  - 贡献 2 从"轨迹感知最优"改成"按负载族的稳健（最差情况最优）分配"。
  - 贡献 3 有理由，但可赢的空间在这些负载上约 1.3–1.75×。只有测出"同一条轨迹内部分阶段调整"能明显超过稳健固定比例，才值得做成独立贡献。
- 详见 `results/exp4_cache_policy/结论.md`、图 8。

### B：分工型混合（实验 6，`results/exp6_split_hybrid/结论.md`，图 9）

- PLBF + AQF backup + 放行区 LRU 缓存，在 Caida 128/256KiB 下**全面不如** PLBF + LRU 缓存：中位数差 1.25×/1.38×，最差 1.66×/2.09×，没有一个负载更好。

- **判断**：分工型结构不作为贡献，只写一句负面结果。缓存写入要计入成员查询成本，并引用 SkiQF。

## 2026-10-27 实验 8：上限的模型推导与 N_eff（`results/exp8_cap_and_neff/结论.md`，图 11）

- **模型**：PLBF 的 p(f) 曲线 + Zipf 下的 TOP-k / Che-LRU 命中模型，在 s ∈ {0,0.5,0.8,1.1,1.5} 上取最坏情况最好的比例，不拟合常数。
- **N 取全集时**：在装得下的设置里和规则一致；在装不下的设置里推出的上限太低（Caida 128/256、Shalla 256 最差 8–32×）。原因是最差的负载只查一个小的活跃集合。**上限问题本质上是 N 的问题。**
- **把 HLL（2KB，误差 ≤7.3%）在整个生命周期上估出的 N_eff 直接代入模型**：
  - 8 个设置里，中位数代价在 1.02–1.05×（COD 1MiB 除外，网格太粗），最坏代价 6 个在 1.9× 以内；

- **限制**：N_eff 用的是全程统计，带后见之明；只看前 10% 查询会低估，最差 3.5–20×。真正在线的估计（外推不同 key 数的增长，或定期重设比例）还没做。

## 2026-10-27 实验 9：误报流模型、只增不减控制器、敏感性、真实轨迹（`results/exp9_fp_stream_controller/结论.md`，图 12）

- **核对前提**：漂移下"不同误报 key ÷ 不同负 key"= 2.07%，和静态 FPR（1.94%）几乎一样。所以漂移的问题出在误报**有多集中**，而不在误报 key **有多少**。
- **误报流模型**：
  - 测三个量：Q_F（计数器）、D_F（HLL）、前 256 个误报 key 的查询占比（Space-Saving）；
  - 由它们拟合误报流的 (W, s_F)；
  - 新增误报按加性计入，缓存按 Che-LRU 计算。

  在 11 个设置（含真实轨迹）上，最坏代价 1.03–1.83 倍，中位数 1.00–1.08 倍。Caida 256KiB 的漂移从 7.5 倍降到 1.01 倍。不需要声明 N、偏斜度范围或 Q。
- **只增不减控制器**：只用前缀里自洽的测量，检查点前密后疏。中位数 1.08–1.26 倍，最坏 1.27–2.5 倍（COD 1MiB 5 倍，但每百万次查询只多 280 次）。改放行的损失中位数 1.004，最大 1.28。
- **真实轨迹**（Caida 按流）：s_F ≈ 1.13，Q_F/D_F ≈ 8.3。误报流模型 1.07–1.21 倍，控制器 1.17–1.87 倍，固定 40% 是 3.4–3.7 倍。全程没有调参。
- **敏感性**：8b 模型对偏斜度范围和 Q（偏差 ±4 倍）不敏感。
- **负面结果**：
  - 新增误报按比例缩放会在漂移下选出过小的缓存；
  - 用不同数反推 s_F 不可辨识；
  - Space-Saving 不用下界时会严重高估集中度。
- **判断**：贡献 2 改用误报流模型，贡献 3 用只增不减控制器，都已有数据支撑。实验这条线可以收束，开始写稿；缺口只剩定理的严格化，以及"控制器代价上界"的证明。

## 2026-10-28 实验 11：补原版 Stacked 与原版 Gama（`results/exp11_original_baselines/结论.md`，图 14）

- **原版 Stacked**（Deeds 等人 C++，HTTYF 仓库自带）：在这些预算下最坏差几百到几百万倍。它本身不用模型，而且每成员不到约 3 bit 时，优化器会产生 0 个哈希、接受全部 key 的退化层。

  - 选的树数和 48 差别很大（16 到 200）；
  - 在无重复的负载（每 key 一次、全新对抗、Caida 全池均匀）上最好；
  - 在重复负载和真实轨迹上差 3–几十万倍。
- **我们方法的最坏代价因此升到 2.15–2.60 倍**，差距全部出在无重复负载上，原因是固定 48 棵树。
- **判断**：Gama（模型对过滤器）与误报流模型（缓存）是互补的。下一步把 Gama 的模型大小搜索并入误报流模型的联合分配，这也是贡献 2 最自然的形式。

## 2026-10-28 实验 12：Gama＋缓存（Gama 是 r=0 的特例）与高预算对比（`results/exp12_gama_cache/结论.md`，图 15）

- **做法**：对 Gama 的每个候选树数，用误报流模型选缓存比例，取联合最优。换模型时 s_F 沿用，W 和 Q_F 按估计 FPR 换算。修了一个 bug：观测误报为 0 时所有候选打平，结果选中 1 棵树。
- **结果**：
  - 15 个设置（含 4 个每成员 ≥10 bit 的高预算）上，中位数 1.00–1.02 倍；最坏代价除两处外都 ≤1.5 倍：Caida 128KiB 2.46 倍、COD 4MiB 每百万次查询多 1.1 次。
  - 无重复负载上和 Gama-PLBF 的差距 ≤1.12 倍，所以"Gama 是特例"在数据上成立。
- **高预算**：原版 Stacked 和纯 AQF 都正常工作（实际位数等于预算），但每百万次查询仍多出几百到几千次误报；Gama＋缓存在 0–149 次之间。
- **换算验证**（293 组）：W 和 Q_F 的换算÷实测中位数都是 0.99，但 10–90 分位较宽（0.57–1.41 和 0.24–1.67）。
- **判断**：贡献 2 定为 Gama＋缓存。在线控制器配 Gama 模型仍会过冲（最坏 1.4–32 倍），需要单独修。

## 2026-10-28 实验 13：可部署版本与控制器修正（`results/exp13_deployable/结论.md`）

- **确认**：实验 12 的 Gama＋缓存是用整条轨迹测的，带后见之明。
- **学习期校准版**（只用前 25% 测，在后 75% 上评估）：低预算最坏 2.46 倍，各设置最坏的中位数 1.40 倍，和全程测量版几乎一样。**主结果改用这个可部署版本。**
- **控制器**：阻尼、阈值、两者都开，最坏仍有 32–35 倍，没修进 3 倍以内，按约定停止，转入讨论。
  - 诊断：这次最坏的那一处是滞后（从 0 开始加，加够之前热点一直误报），而且是 FPR 接近 0 的负载上相对倍数被放大；实验 10 里 COD 256KiB 那次才是过冲。
  - 换成绝对代价看，控制器在漂移设置下比学习期校准版好：COD 256KiB 613 对 6,427，Caida 1MiB 427 对 5,707（每百万次查询）。
- **实验冻结**：剩下的只有第二条真实轨迹和端到端吞吐。

## 2026-10-28 实验 14：离线校准＋在线补充（`results/exp14_warm_controller/结论.md`）

- **做法**：控制器从学习期校准选出的 (树数, 缓存比例) 出发，之后只增不减。
- **结果**：
  - 平稳负载上，从离线起步消除了滞后（31.9 倍降到 4.00 倍），但仍比学习期校准版差（最坏 4.00 倍对 1.44 倍，原因是过冲）；
  - 难负例漂移上没有保住优势，学习期校准版本身已能看到学习期末尾的热点。
- **判断**：两条判据都不满足，维持现状。主方法是 Gama＋缓存（学习期校准），控制器写进讨论。
- **清理**：关掉了 8 个遗留的等待循环。它们用 `pgrep -f` 等待实验进程，但会匹配到自己的命令行，所以永远不会结束，最长的挂了 14 小时。以后等待改用检查结果文件是否存在。
- **实验冻结**：剩下的只有第二条真实轨迹和端到端吞吐。

## 2026-10-28 第二条真实轨迹：MAWI 2020（`results/real_traces/结论.md`）

- **为什么是 MAWI**：CAIDA 其他时段要签协议，拿不到。MAWI（WIDE 骨干网，日本）可以公开下载；取 2020-04-08 的前 1000 万个包，处理流程与 caida_flow 相同。
- **特征口径修正**：tcpdump `-q` 输出的是净载荷长度，TCP 纯 ACK 为 0，几乎直接泄露协议。已改成 IP 包总长，和 Caida 一致。
- **轨迹性质**：模型几乎完美（Gama 选 1 棵树，40KiB 估计 FPR 0.014%），绝对误报很少。
- **结果**：Gama＋缓存（学习期校准）在 40/48/64/128KiB 下都是最好，误报约为 Gama 的 1/2.6（每百万次查询 9.2 对 24.0），原版 Stacked 和纯 AQF 差几千到几万倍。这条轨迹支撑的是"不退化、仍有剩余收益"。
- **第三条（MAWI 2021）**：服务器限速，在后台慢慢下载，下完按 README 处理。
