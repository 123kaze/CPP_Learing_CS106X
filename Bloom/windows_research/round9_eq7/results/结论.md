# 结论：式 (7) 的有限窗口修正（离线诊断，2026-11-03）

逐项数据见 `report.md`。这是诊断，不是新方法：RA6 不变，也没有重新冻结。

## 问题成立

冻结的 RA6（`round6_bucket/src/ra6.py:50`）和 RA4 的候选表（`round4_ra_plbf/src/ra4.py:129-136`）都用

m(T) = a + (λH − a)·e^{−λT}，a = 1 − e^{−λH}

来算一个 key 在评估窗口里的缺失数。它对每次重复都按 e^{−λT} 记缺失，但窗口只有 H 长，窗口内重复的间隔不可能超过它到窗口起点的距离。同样在泊松到达和 Che 近似的假设下，准确的期望是：

- T < H 时，m(T) = a + e^{−λT}·[λ(H − T) − (1 − e^{−λ(H − T)})]；
- T ≥ H 时，m(T) = a。

占用量那一项已经用了 min(T, H)，缺失数这一项没有。原式恒偏大。

验证情况：

- 审稿人的算例（λH = 1，T = H）：原式 0.767，修正式 0.632。
- 直接模拟 5 组 (λ, T)（固定保留时间、冷启动，每组 10 万次）：修正式与模拟一致，误差不超过 0.002；原式最多偏高 23%（λH = 1，T = H/2：0.855 vs 0.697）。

## 离线重算

用 E3 的同一批候选，按 RA6 的方式从实际桶负载重新预测，每个候选都分别用原式和修正式算一遍。范围是合成 14 个设置 × 种子 1–4，共 848 个案例、8480 个已实测的候选；另外加上 MAWI 2024 的全部候选。

用原式算出的每个预测都与 E3 的存档逐位一致（代码里有断言），说明重建的结构和原来完全相同。评估段的实测误报直接取自 E3，没有重新模拟。

## 结果（误报 ≥30 的案例；指标在 RA6 的前 5 短名单内计算）

| | 带符号误差中位，原式 → 修正 | 选择改变 | 修正后的选择 / 原选择的实测误报 |
|---|---:|---:|---:|
| 100万 key 池 | +32.4% → +24.6% | 17% | 0.9989 |
| 全部 key 池 | +35.8% → +30.6% | 19% | 0.9998 |
| 1万、10万 key 池 | 基本不变 | 1–4% | 1.000 |
| 每 key 一次 / 全新对抗 | 不变 | 0% | 1.000 |
| 合计 587 个案例 | +2.4% → +1.8% | 9% | 0.9997 |
| MAWI 2024，4 个预算 | +38%–56% → +36%–55%（128KiB：+205% → +205%） | 0/4 | 1.000 |

误报 <30 的 261 个案例完全不变。这些案例的缓存装得下全部误报 key，T ≥ H，两式都等于 a。

## 可以说的

1. 原式确实偏大，修正式在同样假设下是准确的，论文应该改成修正式，或者明确写成近似。
2. 对 RA6 的选择几乎没有影响：只有 9% 的案例换了配置，换完后实测误报总量只少 0.03%；MAWI 2024 上一个都没换。论文里可以写"修正后 9% 的案例选择不同，实测误报变化小于 0.1%"。
3. **它不能解释预测为什么偏高。** 大 key 池的偏差只从 +36% 降到 +31%，MAWI 2024 短名单上的 38%–56% 几乎不变。原因是：在缓存紧张的情况下 λT 很小，两式的差别也很小。所以不要写成"偏高是式 (7) 造成的"。偏高的真正来源见下一节。

## 偏高从哪里来（按学习期见过 / 没见过的 key 拆分）

逐项数据见 `bias_split.md`，脚本是 `src/bias_split.py` 和 `src/report_split.py`。做法如下：

- 对每个 E3 案例里 RA6 选中的结构，按 key 记录评估段的实测缺失数；
- 预测和实测都拆成"学习期见过的 key"（式 7）和"没见过的 key"（式 5：G_i = H·N1/L·h_i，全部当作缓存挡不住）两部分；
- 实测总误报与 E3 存档逐个一致（断言）。

**合成负载的大 key 池：偏高主要来自没见过的 key，原因是式 5 忽略了它们的重复会被缓存挡住。**

| 分组（误报 ≥30） | 相对误差中位 | 来自未见 key | 来自见过的 key | 未见 key：预测 / 无缓存实测 | 无缓存 / 有缓存实测 | 未见 key 平均被查次数 |
|---|---:|---:|---:|---:|---:|---:|
| 100万 key 池 | +35% | +22% | +3% | 1.02 | 1.19 | 2.6 |
| 全部 key 池 | +37% | +29% | +5% | 1.00 | 1.15 | 1.8 |
| 10万 key 池 | +2% | +6% | 0% | 1.00 | 2.74 | 3.6 |

- 式 5 估的未见 key 查询量是准的：Good-Turing 量与实际之比为 1.00，按分段 FPR 分配后与无缓存时的实测之比为 1.00–1.02。
- 但这些 key 在评估段平均被查 1.8–3.6 次。第一次查询之后，重复的查询会被缓存挡住，式 5 却把每一次都算作缺失。
- 学习期见过的 key（式 7）只多算 3%–5%。

**MAWI 2024 真实轨迹：来源不同。** 小预算下偏高主要来自见过的 key，未见 key 那部分的两个误差大体抵消。

| 预算 | 相对误差 | 来自未见 key | 来自见过的 key | Good-Turing 未见查询量 / 实际 | 未见 key 无缓存 / 有缓存实测 |
|---|---:|---:|---:|---:|---:|
| 16KiB | +59% | −17% | +75% | 0.39 | 2.85 |
| 24KiB | +46% | −6% | +52% | 0.39 | 3.78 |
| 32KiB | +25% | −5% | +29% | 0.39 | 5.16 |
| 128KiB | +205% | +205% | 0% | 0.39 | 1.00 |

- 真实流量不平稳：评估段里没见过的 key 的查询量，是 Good-Turing 估计的 2.6 倍。新流在不断出现。
- 缓存挡掉了这些新 key 的大部分误报，抵消了上面那项低估。
- 见过的 key 被高估 29%–75%。最可能的解释是流有寿命：学习期活跃的流，到评估段往往已经结束，按学习期速率外推会偏高。这一条**没有直接验证**。
- 128KiB 下误报只有个位数（未见 key 部分预测 3 次、实测 1 次），+205% 是小数目造成的比值，没有意义。

**对论文的含义：**

- 偏高的主因不是式 (7)。在合成负载上，主因是"未见 key 一律算作缓存挡不住"这个保守假设；在真实轨迹上，主因是速率的非平稳性。
- 可以这样写：式 5 有意保守，未见 key 的重复查询没有计入缓存收益，所以在 key 池很大的负载上预测会系统性偏高。由于 RA6 只在前 5 个候选里比较相对大小，这个偏差对选择的影响有限（E3：前 5 内 Spearman 中位 0.90）。
- 如果要改进方法，最直接的是对未见 key 也用 Good-Turing 估计它们在窗口内的重复。这属于新方法，需要新一轮冻结和新的验证集。

## 必须保留的条件

- 只修正了 RA6 最后按实际桶负载重新精算的那一步。RA4 的候选表（短名单和分段权重）也用了原式。如果要做完整的修正版方法，权重和短名单都会变，就得作为新一轮重新冻结、重新实测。
- MAWI 2024 已经用作过一次性留出集，这里只当作诊断。新方法需要新的独立验证集。

## 附：审稿人的 TCP/UDP 质疑

这一条与式 (7) 无关，但它会影响论文里怎么回应审稿人。

- **已核对：严格记账各轮（round2–round6）的真实轨迹模型只用两个特征 `src, dst`。** 依据是 `round2_backlog/src/prepare_datasets.py` 的特征选择，以及 6 个 `*_flow` 缓存的特征列。
- 早期 `learned_adaptive_hybrid`（实验 1–14）的 `caida_flow` / `mawi2020_flow` 还用了包长统计（`len_mean/len_min/len_max`），包长与协议相关。如果论文引用了那一批真实轨迹的数字，就不能说"模型只用地址"。
- 地址按 float32 存储，IPv4 的有效精度约为 /24 前缀。
- 按模型实际看到的这个精度，负例流中与某个成员流 `(src, dst)` 完全相同、模型无法区分的比例为：

  | 数据集 | 比例 |
  |---|---:|
  | caida | 3.2% |
  | MAWI 2020 | 3.2% |
  | MAWI 2021 | 9.8% |
  | MAWI 2022 | 7.6% |
  | MAWI 2023 | 9.0% |
  | MAWI 2024 | 27.3% |

  这可以支持"学习任务本身不平凡"。但这样构造任务的问题仍然存在，最好的回应还是补一个协议一致的实验。
