# 端到端计时口径

`src/end_to_end.py` 在单线程 Numba 编译循环内处理真实成员和非成员请求。每次查询现场计算 key 哈希；需要模型时逐节点遍历从 LightGBM 导出的数值树；使用实际位打包 BF 和紧凑 CLOCK 缓存。插入缓存时现场二分查询全部成员哈希的有序索引，取得安全前缀。计时包括缓存查找、替换、插入以及两个 HLL、一个计数器和 Space-Saving 表的更新。

特征数组作为过滤器 API 的输入；从原始对象抽取特征的开销不包含在计时中。模型构建、输入轨迹生成、JIT 编译、25% 前缀预热和真正的磁盘/网络后端 I/O 也不计入。后 75% 查询的总时间除以查询数，重复运行后报告各次平均值的中位数，原始重复值全部保留。后端 1、10、100 微秒是串行访问代价投影：`实测过滤时间 + (真阳性数 + 误报数)/查询数 × 后端延迟`。投影吞吐不代表真实存储系统吞吐，也没有建模并发和批处理。

输入含 10% 或 50% 真成员；负查询分别来自全部测试非成员的均匀分布和 1 万个非成员上的 Zipf(1.1)。两种缓存放置使用完全相同的混合轨迹和初始状态，每种配置独立预热，评价区间与正确性计数均相同。固定配置的预热不涉及学习后重放选择出的配置；若要用于自适应选择后的部署成本，还需计入重建和状态迁移。

压缩前缀有可能额外命中一个本来就会被过滤器拒绝的非成员。前置缓存会更新该前缀的 CLOCK 引用位，后置缓存跳过这次查找，因此替换状态和后续误报数存在微小差别的可能。程序逐项保存两种放置的实际误报数及差值，不预设压缩缓存两种放置的误报率必然严格相等。任何真成员被缓存拒绝都会导致验证失败。

过滤器、模型、导航数组和草图按实际可执行的紧凑数组负载及 ndarray 对象头计费，同时计入模型数组字典和缓存对象头。Python 解释器、JIT 机器码、输入数据和成员验证索引的内存另列；这不等于整个 Python 进程的 RSS。成员索引是假定部署可提供的外部权威辅助索引，其体积随成员数线性增长；缺少该索引的部署不能直接声称整个系统仍在给定过滤器预算内。

树表示使用 int16 特征/孩子/根索引和 float64 阈值/叶值；最多 200 棵、每棵 31 叶的模型满足索引范围，超出会显式拒绝。原生遍历与 LightGBM 的原始分数逐样本核对。`src/test_end_to_end.py` 的输入为合成组件测试，只证明代码路径和安全性，不作为 COD/Caida 实验效果证据。
