# E7–E9：查询速度、端到端（SQLite）与冷启动（单线程）

每种方法用的都是它自己在学习期选出的结构（与第五、六轮主表相同，seed 0）。查询路径用 numba 实现：先查缓存，未命中时在紧凑模型数组上逐棵遍历树（用查询 key 的真实特征），再定位 DP 区域，最后检查 BF；误报时在成员哈希里二分查找，得到安全前缀并插入缓存。
每个方法都做了三项断言：遍历得到的分数与 LightGBM 一致；所有成员都被接受；评估段的误报总数与主表的 fp_tail 逐位相同。
learned stacked 和 SkiQF 式准入在第二轮的引擎里，这里没有计时。

## 结论

- **查询速度由选中的树数决定，缓存和 BF 只占小头。**
  - 在 COD、Caida 上，三种方法都选了 160 棵树，每次查询 2.8–3.7 微秒，其中模型遍历占 94–98%；有没有缓存，相差不到 2%。
  - 选了更少树的方法查询更快：Shalla 上 RA6 选 32 棵树，548 纳秒，Gama 选 48 棵树，755 纳秒；URL 上 Gama 选 16 棵树，280 纳秒，RA6 和网格选 48 棵树，约 730–750 纳秒。
  - 所以"带缓存会不会拖慢查询"这个问题，答案主要取决于选出来的树数，而不是缓存本身。
- **真实轨迹上（1–4 棵树），模型只要 28–79 纳秒，缓存探测就占了相当比例。** RA6 每次查询比 Gama 慢 5–39 纳秒（例如 MAWI 2021：108 对 74 纳秒）。
- **端到端：误报省下的后端访问能不能抵过查询开销，取决于后端有多贵。**
  - 文件型 SQLite（实测每次约 3–4 微秒）上，真实轨迹的 RA6 总耗时是 Gama 的 0.47–0.72，因为后端访问少了 40–65%。Shalla 上是 0.77。
  - URL 128 上 RA6 反而慢 1.7–2.1 倍：它选了 48 棵树，而 Gama 只选 16 棵，可省下的误报只有 52 次，补不回模型变重的代价。这是"只按误报数选配置、不管查询开销"带来的副作用，要如实写进论文。
  - COD、Caida 上 160 棵树的模型（约 3 微秒）和一次文件型 SQLite 查询差不多贵，所以任何学习型过滤器和不用过滤器相比都没有优势。内存型 SQLite（不到 1 微秒）上，学习型过滤器反而更慢。
  - 按推算，后端延迟达到 50 微秒以上时，端到端时间基本由后端访问次数决定：真实轨迹上 RA6 是 Gama 的 0.35–0.61，Shalla 是 0.83–0.84，URL 是 1.01–1.08，COD 和 Caida 基本持平（0.96–1.01）。这些都是推算，不是实测。
- **冷启动：两种方法差别不大。**
  - 评估段第 1 个窗口的误报，网格和 RA6 都是稳态的 1–3.6 倍，比例很接近；除 COD（1 对 3 次）外，RA6 第 1 个窗口的误报都不多于网格。
  - "稳态窗口"的定义是：从这个窗口起，窗口误报率一直保持在最后 25% 平均值的 ±10% 以内。"无"表示一直达不到，通常是因为窗口误报太少、波动太大。这个指标对噪声很敏感，比如 Caida 256：网格 72，RA6 91；Shalla：59 对 95。所以不宜单独下结论。
- learned stacked 和 SkiQF 式准入的查询速度没有在这里重测。SQLite 只用来示例后端代价，没有清空操作系统缓存。
