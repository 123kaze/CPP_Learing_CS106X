### 7.5 为什么这组结果和论文 Table 2 不一致

这组结果不能直接对标论文里的 LBF / G-LBF，主要原因如下：

1. 论文 URL 的默认流程不是随机 70/30 stratified query。老师代码 `bf_url_main.py` 里原始切分逻辑是：所有正样本 + 80% 负样本作为 train/test，剩余 20% 负样本作为 query。因此 query 主要是负样本，用来测 FPR。当前评估脚本用了重新 stratified split。

2. 论文里的学习模型大小默认约 39KB；第一次 5 轮实验里老师 LightGBM 模型只有约 21KB：

```text
URL teacher model_bits = 171224 bits ≈ 20.9 KiB
COD teacher model_bits = 186848 bits ≈ 22.8 KiB
```

这和论文设定不一致。论文 LBF 固定默认模型大小，G-LBF 会搜索模型和 BF 的内存分配。

3. URL 特征没有严格复用老师的 `embedding_gene/url_embedding.py` 输出。当前脚本用了轻量 URL 统计特征；论文结果使用的是老师预处理后的 `dataset/url.csv/url_train.csv/url_test.csv/url_query.csv`。

4. COD 数据也不一致。论文表里 COD 是：

```text
positive = 2,498,077
negative = 2,980,291
total = 5,478,368
```

当前 Kaggle 解压后我们读到的是：

```text
positive = 3,000,000
negative = 3,000,000
total = 6,000,000
```

说明 COD 的标签定义、采样或文件版本没有对齐论文。

5. 当前脚本里的 teacher LightGBM-LBF 只是按老师 LBF 结构临时训练 5 轮，不是运行老师仓库的 `lgb_url_LBF_main.py` 或 `lgb_url_GamaLBF_*` 原流程。

因此，第 7 节只能作为“同一脚本下的第一次工程对比”，不能作为论文复现结果。

通用 raw feature 搜索没有追上 G-LBF，并且整体弱于 URL-aug 版本。这说明：

```text
1. 只靠 segments / threshold / C 的 Gama-like 搜索不够。
2. 轻量单投影模型的表达能力明显弱于 LightGBM。
3. URL 专属增强特征确实带来收益，但这会降低跨数据集公平性。
```

如果坚持公平、通用地超过 G-LBF，下一步不能靠手写 URL 特征，而应该换成通用模型增强：

```text
PolynomialFeatures(degree=2, interaction_only=True)
或小型随机投影 ensemble
或 shallow MLP / tiny tree ensemble
```

其中最接近 Gama 思路的是：

```text
G-Student-LBF = 通用模型族搜索 + 内存分配搜索 + threshold 搜索
```

## 13. 多投影 Piecewise 尝试

实现方式：


## 14. Raw-PLBF-Student 尝试

本轮实现 PLBF-style student：

```text
raw features
  -> ridge/logistic score
  -> K 个 score bucket
  -> 每个 bucket 单独统计 positive/validation-negative density
  -> DP/coarse allocation 给每个 bucket 分配 backup BF bits
  -> query 时进入对应 bucket BF
```

这个版本没有 URL 专属增强特征，只用老师 `url.csv` 里的 raw features。它和前面单 threshold LBF 的关键区别是：

```text
单 threshold LBF: 一个全局 backup BF
Raw-PLBF-Student: 多个 bucket-specific BF，并为每个 bucket 分配不同内存
```

## 15. Raw-PLBF Allocation Granularity and Bad Bucket Diagnostics

根据 `下一步.md`，本轮先做两个实验：

```text
1. 细化 allocation step_bits
2. 输出 per-bucket 误报归因，找坏桶
```

### 15.1 Greedy allocation 失败记录

先实现了一个快速 greedy allocation，用来支持更小 step。结果明显变差：

```text
64 KiB best query_fpr ≈ 8.685%
128 KiB best query_fpr ≈ 1.459%
192 KiB best query_fpr ≈ 0.302%
```

原因是 Bloom FPR 对 bits 的收益曲线不是简单适合从 0 bits 贪心爬升的形状。某些 bucket 需要先投入一段 bits 才有明显收益，greedy 容易陷入局部选择。因此后续仍使用精确 DP。

### 15.2 精确 DP + step_bits=1024

运行命令：

```powershell
python .\Bloom\tune_student_url_plbf.py --memory-kib 64 128 192 256 320 --models ridge logistic --c-values 0.1 1 10 --bucket-counts 8 16 32 --step-bits 1024 --allocation dp
```

结果：

| Memory | Best model | Buckets | FPR |
|---|---|---:|---:|
| 64 KiB | ridge C=1 | 32 | 7.207% |
| 128 KiB | ridge C=1 | 32 | 1.325% |
| 192 KiB | logistic C=10 | 32 | 0.340% |
| 256 KiB | logistic C=10 | 32 | 0.096% |
| 320 KiB | logistic C=10 | 32 | 0.032% |

和 step_bits=4096 相比：

```text
64 KiB: 7.441% -> 7.207%
128 KiB: 1.386% -> 1.325%
192 KiB: 0.349% -> 0.340%
256 KiB: 0.102% -> 0.096%
320 KiB: 0.023% -> 0.032%  # 略差，validation/query 差异或 BF 随机性
```

### 15.3 精确 DP + step_bits=512

只针对 64/128/192 KiB 跑 16/32 buckets：

```powershell
python .\Bloom\tune_student_url_plbf.py --memory-kib 64 128 192 --models ridge logistic --c-values 0.1 1 10 --bucket-counts 16 32 --step-bits 512 --allocation dp
```

结果：

| Memory | Best model | Buckets | FPR |
|---|---|---:|---:|
| 64 KiB | ridge C=1 | 32 | 7.153% |
| 128 KiB | ridge C=10 | 32 | 1.335% |
| 192 KiB | logistic C=10 | 32 | 0.352% |

结论：

```text
512 bits 比 1024 bits 只在 64 KiB 略好；
128/192 KiB 没有稳定改善。
allocation 粒度不是主要瓶颈。
```

### 15.4 64 buckets + DP 1024

进一步把 bucket_count 增到 64，近似更细 bucket boundary：

```powershell
python .\Bloom\tune_student_url_plbf.py --memory-kib 64 128 192 --models ridge logistic --c-values 0.1 1 10 --bucket-counts 64 --step-bits 1024 --allocation dp
```

结果：

| Memory | Best model | Buckets | FPR |
|---|---|---:|---:|
| 64 KiB | ridge C=10 | 64 | 7.086% |
| 128 KiB | ridge C=10 | 64 | 1.371% |
| 192 KiB | logistic C=10 | 64 | 0.322% |

这个结果说明：

```text
更多 bucket 对 64/192 KiB 有小幅收益；

```
