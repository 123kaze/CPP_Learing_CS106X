它用了老师思路里的几个核心点：

```text
1. 用树模型产生 score
2. 不均匀利用 score distribution
3. 在固定 memory budget 下分配 model bits / BF bits
4. 用估计 FPR 指导搜索，而不是每个候选都盲目试
```

但它还不是老师 Gama 的完整算法。老师 Gama 更完整的部分包括：

```text
1. 在 learning model size 和 backup BF size 之间做自适应搜索
2. 搜索 LightGBM boosting rounds / model size
3. 对每个模型轮数做 threshold selection
4. 用排序 + 滑动统计把 threshold search 从 O(n²) 降到 O(n log n)
5. 用 Bayesian Optimization 搜索 memory allocation / model 参数
```

我这版保留的是你自己的 PLBF 路线，所以没有退回老师的单 threshold Gama-LBF，而是做了一个混合版：

```text
Gama-like lighttree scorer
+
Student Raw-PLBF bucket allocation
+
query-like validation split
```

更准确地说，它是“借鉴老师 Gama 思想的 LightTree-PLBF”，不是老师原版 Gama-LBF。

1. **LightTree scorer 比 ridge/logistic 更会分 URL**
   
   原来的 ridge/logistic 本质上是线性打分，只能学一个比较粗的方向。URL 特征里很多模式是非线性的，比如长度、数字比例、特殊字符、host/path/query 结构之间的组合关系。小 LightGBM tree 能切这些组合区域，所以 score distribution 更干净。

2. **PLBF 比单 threshold 更会用 score**
   
   单阈值 LBF 只有一句话：

   ```text
   score >= threshold 直接接受
   score < threshold 查 backup BF
   ```

   但 PLBF 会把 score 分桶，并给不同桶分配不同 backup BF 内存。也就是说，它不是只问“过不过阈值”，而是问：

   ```text
   这个 score 区间有多少正样本？
   有多少负样本？
   值不值得多给 bits？
   ```

   所以同样的 scorer，PLBF 通常比单 threshold 更省误报。

3. **query-like validation 让 DP 学得更接近真实 query**
   
   你之前发现的问题是：

   ```text
   validation negative 很少
   query 时却爆 FP
   ```

   这说明 DP 看到的负样本分布和真实 query 不一样，于是内存分配会偏。现在 `query_split` 用真实 query negative 的一半来估计 bucket 权重，所以 DP 分配 bits 时更贴近最终测试分布。

4. **老师 G-LBF 优化的是 LBF 结构，不是 PLBF-style 多桶结构**
   
   你现在是：

   ```text
   lighttree scorer + score bucket + per-bucket BF allocation
   ```

   老师 G-LBF 更像是：

   ```text
   LightGBM scorer + single threshold + backup BF memory optimization
   ```

   所以你的结构在高内存档位更容易赢，因为它能把额外内存精确投给“坏桶”。


这样更新范围从：

新增 positive 不直接重建原 BF，而是进入 delta BF：

```text
bucket_i:
```

```text
K buckets, total memory M
```

```text
dirty buckets + neighbor buckets
```


之间重新分配 bits。

这样 construction time 会明显下降。

```text
query 本来应该是 held-out evaluation set。
如果我们从 query 里拿一部分 negative 来做 validation，
那它就不再是完全未见测试集。
```

这会影响三件事。

**1. 公平性**
如果 teacher G-LBF 没有用 query 信息，而你的 LightTree-PLBF 用了 query negative 的一半来调 DP 分配，那对比不完全公平。

更严谨的表述应该是：

```text

```

而不是直接说：

```text
LightTree-PLBF 公平超过 G-LBF
```

除非你也让 teacher 方法使用同样的 validation/query split，或者单独准备一个新的 final test set。

**2. 学术性**
学术论文里，测试集必须尽量只用于最终评估。用 query 的一部分做 validation，容易被认为是 test leakage。

虽然你没有用 query label 训练 scorer，也没有用最终 evaluation half，但你确实用了 query distribution 来优化 bucket memory allocation。所以这是弱泄漏，不是严重作弊，但必须写清楚。

比较稳的说法是：

```text
We study a transductive/query-aware setting where a sample of future query distribution is available for calibration.
```

中文就是：

```text
我们研究的是 query-aware calibration 场景，即系统可以获得一小部分未来查询分布样本用于校准内存分配。
```

这样它就不是“偷偷用了测试集”，而是一个明确的问题设定。

**3. 实用性**
实用性反而不一定差。很多真实系统确实有 query log：

```text
CDN / 安全过滤 / URL blacklist / database cache / key-value store
```

系统可以拿历史 query negative 或近期 query log 来估计未来查询分布。所以 query-like validation 在工业上是合理的。

但你要把它解释成：

```text
使用历史查询日志，而不是使用测试集答案。
```

这就学术上更站得住。

更推荐你改成三种设置：

| Setting | 含义 | 学术公平性 |
|---|---|---|
| sample validation | 只用 train/test/sample，不碰 query | 最公平 |
| query-log calibration | 用历史 query log 校准 bucket 权重 | 实用设定 |
| final held-out query | 完全不参与训练/调参，只最终测试 | 最终报告结果 |

你现在的 `query_split` 可以改名或解释成：

```text
query-log calibration split
```

然后再做一个更严谨的数据划分：

```text
原始 query negative
  -> calibration_query_neg  用于 DP
  -> final_query_neg        只用于最终测试
```

这比“用 query 做 validation”好听，也更学术。

最终汇报时建议这样讲：

```text
为了诊断 validation/query distribution mismatch，
我们额外研究了 query-aware calibration setting。
该设定假设系统可以访问一小部分历史查询日志，
用于估计 bucket-level negative distribution。
最终 FPR 仍在未参与校准的 held-out query split 上评估。
```

然后强调：

```text
这不是完全 supervised test leakage，
因为 calibration split 只提供 query distribution，
不参与 scorer training，
也不参与最终 held-out evaluation。
```

但是最公平的最终结论要分开写：

```text
在 standard setting 下：Raw/LightTree-PLBF 使用 sample validation。
在 query-aware setting 下：LightTree-PLBF 使用 query-log calibration，性能更强。
```

一句话：  
**会影响公平性，所以不能混着讲；但如果你把它定义成 query-log calibration / transductive setting，并保留 held-out query evaluation，它就可以成为一个合理且有实用价值的研究设定。**

**OpenAI Codex**

因为你现在赢的地方，主要不是“同一棵树更强”，而是 **PLBF 的结构优势 + query-aware bucket 分配**。老师的 Gama-LBF 即使用同样的 LightGBM tree，也不一定能达到你的 LightTree-PLBF 效果。

可以这么理解。

老师 Gama-LBF 大体是：

```text
LightGBM score
  -> single threshold
  -> one backup BF
```

它优化的是：

```text
模型大小
threshold
backup BF memory
```

但最后仍然只有一个全局决策边界。

你的 LightTree-PLBF 是：

```text
LightGBM score
  -> many score buckets
  -> per-bucket positive/negative density
  -> per-bucket BF memory allocation
```

也就是说，你不是只问：

```text
score 高不高？
```

你问的是：

```text
这个 score 区间里，正样本有多少？
负查询有多少？
给这个区间多少 bits 最划算？
```

这比单 threshold 细很多。

举个直观例子：

```text
bucket A: 正样本很多，负查询也很多 -> 多给 bits
bucket B: 正样本很多，负查询很少 -> 少给 bits
bucket C: 正样本少，负查询很多 -> 很划算，多给 bits
```

Gama-LBF 的单 backup BF 没法做这种区别。它只能把所有低于 threshold 的 positive 混在一个 BF 里。这样某些“高风险 score 区间”会被低风险区间稀释，内存不能精确投放。

所以即使用同样的树：

```text
Gama-LBF:
    score 用得粗

LightTree-PLBF:
    score 用得细
```

这就是第一层原因。

第二层原因是你用了 query-like calibration。Gama 默认优化的是 sampled validation distribution，不一定像真实 query。你的 DP 分配用的是 query split，所以它更知道：

```text
哪些 bucket 在真实 query 中更容易出负样本
```

于是它会把内存投给真实 query 中更危险的 bucket。Gama 如果没有同样使用 query-aware validation，就会吃亏。

第三层原因是 Gama 的优化目标和你的优化目标不同。

Gama-LBF 更像优化：

```text
overall FPR = model false accept + backup BF FPR
```

而你的 PLBF 优化：

```text
sum over buckets:
    query_neg_weight_i * BF_FPR(bits_i, positives_i)
```

它直接按 bucket 加权优化 query negative distribution。这个目标更贴合你的评估方式。

所以答案不是：

```text
我的树比老师树神奇
```

而是：

```text
同样的 tree score，Gama-LBF 仍然受限于 single-threshold + global backup BF；
LightTree-PLBF 通过 bucket-level memory allocation 更充分地利用了 score distribution。
```

但这里也要小心。你现在最强结果包含 query-aware calibration，所以严格公平说法应该是：

```text
在 query-aware PLBF setting 下，我的方法比 Gama-LBF 更低。
```

1. **same scorer + sample validation**


   这样证明结构优势。
