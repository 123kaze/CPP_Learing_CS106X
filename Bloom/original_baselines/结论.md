# 原版代码基线：结论（2026-10-29）

全部数字见 `report.md`，跑法与改动见 `README.md`。下面的数都是尾段误报总数（对种子取均值，再对负载求和）。"去掉探测重放"的理由见下面第 4 点。

## 1. 我们复现的 Gama 不弱于原版 Gama（回答 B6）

| 设置（去掉探测重放） | 我们的 Gama 式 | 原版 Gama | 原版选的轮数 |
|---|---:|---:|---:|
| COD 256 / 1024 / 4096★ | 1,123,451 / 14,725 / 204 | 2,467,520 / 83,658 / 0 | 12 / 100 / — |
| Caida 128 / 256 / 1024 / 2048★ | 6.98M / 3.28M / 496,127 / 5,482 | 13.57M / 9.26M / 762,295 / 28,411 | 8 / 18 / 38 / — |
| Shalla 256 / 1024 / 2048 / 4096★ | 21.07M / 6.65M / 1.38M / 63,877 | 23.66M / 6.59M / 1.89M / 102,922 | 5 / 14 / 30 / — |
| URL 64 / 128 / 256 | 428,910 / 96,297 / 2,267 | 1,098,690 / 173,074 / 84,799 | 2 / 2 / 2 |
| 真实轨迹（9 个设置） | 全部更少 | 16KiB 放不下，其余多 1.4–3 倍 | 2 |

- 26 个设置里，我们复现的 Gama 在 24 个上误报更少。例外是 COD 4096★（204 对 0）和 Shalla 1024（6.65M 对 6.59M，基本持平）。
- 差距主要来自原版的记账方式：它按 pickle 计模型大小，每棵树约 3.4KB，是紧凑数组的 5 倍左右。所以同样预算下它只能用很少的树，比如 URL 三个预算都只选 2 轮。原版还要求前 5 轮都放得进预算，所以 16KiB 的真实轨迹上直接无法运行。
- 结论：论文里的 Gama 对照不是"故意做弱"的复现。原版代码在同一预算下只会更差。

## 2. 原版 PLBF 分配器在部分设置更好（新发现，需要如实报告）

用同一个模型（Gama 式树数）时，原版 PLBF（FastPLBF，N=1000、k=5 的动态规划）和我们统一的 100 段拉格朗日分配器互有胜负：
- 原版更好：Caida 1024（203,797 对 496,127，好 2.4 倍）、URL 128（54,191 对 96,297）、COD 256/1024、真实轨迹 16/32KiB；
- 我们更好：Shalla 2048/4096、URL 256、MAWI 2021 24KiB 等。

本研究里的所有方法（Gama 式、网格、RA-PLBF）都建在我们这一个分配器上，所以方法之间的比较不受影响。但这说明**分段方式本身还有改进空间**。把 RA-PLBF 的权重交给原版 PLBF 的动态规划分段，是下一步可做的事。

## 3. Stacked、AdaptiveQF、SkiQF 原版

- **Stacked 原版**：低预算下只建 1 层，退化成普通 BF；经常超预算，多数在 1.0–1.34 倍，个别运行达到 4.8–5.2 倍（逐条记录在 `stacked/out/`）。即使多用了内存，误报也比 RA-PLBF 多 1–3 个数量级。
- **AdaptiveQF、SkiQF、HybridSkiQF 原版**：官方实现把槽数取成"成员数/0.95"向上的 2 的幂，余数最少 1 位。所以在常规预算（每 key 约 1–3 bit）下全部放不下，只有 URL 256 和高预算★点能构造。在能构造的点上，误报仍比 RA-PLBF 多 1–5 个数量级。例如 COD 4096★：AQF 75,581，SkiQF 154,130，RA-PLBF 1。
- **SkiQF 比 AQF 误报更多是它的设计使然**："先租后买"省的是适配带来的 I/O，我们只计误报。论文里要说明这一点，不能把它写成 SkiQF 更差。
- **用途**：这些是"不用学习模型"的背景对照，论文里不能当成主要对手。

## 4. 探测重放负载的不对称（协议缺陷，要写进局限性）

"探测重放 10%"负载沿用第二轮协议：重放的是我们 Gama 式结构被观察到的误报 key。所以它只对"Gama"这一行构成定向攻击，每个设置约 75 万次误报，对其他结构是不对称的。上面的对比都去掉了这个负载；含这个负载的原表也保留在 `report.md` 里。
