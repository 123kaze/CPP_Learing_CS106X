**整体运行流程**

假设你写：

```cpp
ThreadPool pool(4);

auto f = pool.submit([] {
    return 100;
});

std::cout << f.get() << std::endl;
```

流程是：

1. `ThreadPool pool(4)` 创建 4 个工作线程。
2. 4 个线程进入 `while(true)`，发现没有任务，于是睡在 `cv_.wait()`。
3. `submit()` 把任务塞进 `tasks_`。
4. `cv_.notify_one()` 唤醒一个线程。
5. 那个线程从队列取出任务。
6. 执行任务，得到 `100`。
7. `packaged_task` 把结果保存到 `future`。
8. `f.get()` 拿到结果 `100`。
9. `pool` 析构时，设置 `stop_ = true`。
10. 唤醒所有线程。
11. 所有线程发现该退出了，结束。
12. 析构函数 `join()` 等它们全部结束。

**User**

为什么slowSquare(8) finished on thread 138927207864000的thread总是和printJob: this task returns void on thread 138927207864000的相同？

---


**OpenAI Codex**

因为你的线程池只有 4 个工作线程，而任务队列是 **先进先出 FIFO**。`printJob` 和 `slowSquare(8)` 总是落到同一个线程，主要是调度节奏造成的。

你提交任务的顺序大概是：

```text
f1: add
f2: lambda return 100
f3: makeMessage
f4: multiply
f5: printJob   // sleep 200ms
slowSquare(1) // sleep 500ms
slowSquare(2)
slowSquare(3)
slowSquare(4)
slowSquare(5)
slowSquare(6)
slowSquare(7)
slowSquare(8)
```

线程池有 4 个线程。前面几个小任务很快完成，然后 4 个线程开始抢后面的慢任务。

关键是：

```cpp
printJob()
```

只睡 `200ms`：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(200));
```

而：

```cpp
slowSquare()
```

睡 `500ms`：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(500));
```

所以执行 `printJob` 的那个线程，比正在执行 `slowSquare(1..3)` 的线程更早空出来。

它空出来以后，会回到线程池循环里：

```cpp
task = std::move(tasks_.front());
tasks_.pop();
task();
```

也就是继续从队列里拿下一个任务。

在你的这次任务排列里，这个线程经常会形成这样的路线：

```text
执行 printJob
很快完成
拿 slowSquare(4)
完成后再拿 slowSquare(8)
```

所以你看到：

```text
printJob: this task returns void on thread 138927207864000
slowSquare(8) finished on thread 138927207864000
```

它们经常是同一个线程。

不过严格说：这不是 C++ 保证的，只是当前机器、当前系统调度、当前任务耗时下很稳定地出现。

线程调度不是完全可预测的。换一台机器、加一点输出、改 sleep 时间、改线程数量，都可能变化。

比如你可以试试把线程池改成 2 个：

```cpp
ThreadPool pool(2);
```

或者把 `printJob` 改慢：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(800));
```

你很可能就会看到不同的分配结果。

核心理解是：

> 线程池不是“任务绑定线程”，而是谁先空下来，谁就从队列里拿下一个任务。  
> `printJob` 那个线程先空下来，所以它后面又拿到了某些 `slowSquare` 任务。

**User**

为什么切换线程代价高呢？

---


**OpenAI Codex**

线程切换代价高，是因为 CPU 不是简单地“换个人干活”这么轻松。它要把当前线程的运行现场保存起来，再把另一个线程的现场恢复回来。

可以把线程想成一个正在做题的人。切换线程就像：

> 你正在写数学题，突然被要求停下，保存草稿、记住做到哪一步、换一本作业、翻到另一题、恢复那道题的上下文，然后继续写。

这个过程本身不产生业务结果，但会消耗时间。

主要代价有这几类。

**1. 保存和恢复 CPU 状态**

每个线程运行时，CPU 里有很多状态：

```text
寄存器
程序计数器 PC
栈指针 SP
标志位
浮点/SIMD 寄存器
```

切走当前线程时，操作系统要保存这些状态。

切到另一个线程时，又要恢复另一个线程的状态。

这些操作都要花 CPU 指令。

---

**2. CPU 缓存失效**

这是很重要的一点。

CPU 很快，内存相对很慢。所以 CPU 会把常用数据放进缓存：

```text
L1 cache
L2 cache
L3 cache
```

线程 A 正在运行时，缓存里可能放着 A 常用的数据。

切到线程 B 后，B 要用的是另一批数据，CPU 缓存可能不命中，就得去更慢的内存里拿。

这叫 cache miss。

所以切换线程不只是“保存寄存器”，还可能让 CPU 原本热乎的缓存变冷。

---

**3. TLB 可能受影响**

TLB 是 CPU 用来加速虚拟地址到物理地址转换的小缓存。

线程切换时，如果切到的是另一个进程，地址空间不同，TLB 影响更大。

同一个进程里的不同线程共享地址空间，所以 TLB 代价通常比进程切换小一些，但仍然可能有影响。

---

**4. 操作系统调度器要参与**

线程不是自己决定谁运行，通常由操作系统调度器决定。

调度器要做一些判断：

```text
哪个线程优先级高？
哪个线程等了很久？
哪个 CPU 核心空闲？
这个线程该不该被唤醒？
```

这些调度逻辑本身也要花时间。

---

**5. 锁竞争会导致更多切换**

比如一个线程拿不到锁：

```cpp
std::mutex mutex;
```

它可能会被阻塞，操作系统把它挂起，然后切到别的线程。

等锁释放以后，再把它唤醒。

这中间又有：

```text
阻塞
调度
唤醒
重新竞争锁
```

如果很多线程都抢一把锁，切换会变得更频繁，性能会明显下降。

---

拿你的线程池来说。

如果任务很多，但每个任务都特别小，比如：

```cpp
pool.submit([] {
    return 1 + 1;
});
```

那线程池可能不划算。

因为任务本身可能只需要几十纳秒或几百纳秒，但是：

```text
提交任务
加锁
入队
唤醒线程
线程取任务
切换上下文
future 同步
```

这些管理成本可能比任务本身还贵。

所以线程池适合：

```text
任务数量多
每个任务有一定重量
或者任务会等待 IO、sleep、网络、磁盘
```

不适合：

```text
超小计算任务
频繁抢同一把锁的任务
任务之间依赖很强，必须排队等
```

一句话总结：

> 线程切换贵，是因为 CPU 要保存现场、恢复现场、重新加载缓存，还要经过操作系统调度；这些成本本身不做你的业务计算，却实实在在占用时间。
